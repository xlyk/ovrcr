# Operator feature inventory and usability review

Reviewed November 5, 2026. Checkout `/Users/xlyk/Code/ovrcr`, branch `main`, revision `08d25641d3ef96a2b8f9f74a5710efb2c532b75a`. Existing unrelated untracked files were preserved. No product code changed.

## Assessment

Operator has substantial conversation and execution functionality. It is most approachable for someone who already understands OVRCR, keyboard focus, provider setup, and terminal terminology. The largest UX gaps are getting connected, knowing what a request will act on, finding older conversations, and recovering from failures without leaving the interface.

This is an expert review grounded in current source and a disposable native app, not a usability study with end users. Features identified in source are distinguished from interactions exercised in this pass. No live Operator provider request was tested.

## What is easy

- **Getting back to Operator:** persistent sidebar placement and global Quick message make entry convenient.
- **Sending a short request after setup:** Enter-to-send, paste-without-send, and the small growing composer are familiar and efficient.
- **Leaving work running:** switching chats or returning to a terminal preserves work and avoids a forced waiting screen.
- **Keeping evidence readable:** compact receipts keep command output from overwhelming the transcript; details remain available.
- **Avoiding accidental loss:** drafts survive navigation and failed submission; closing has confirmation; archived history remains recoverable.
- **Reading on a narrower screen:** the sidebar yields space and the selected chat title appears in the local header. The native 98-column view remained readable.

These are design strengths; response quality, live concurrency and recovery reliability were not retested here.

## Difficulties and recommended changes

| Priority | User-visible difficulty | Evidence and implication | Smallest useful improvement | Acceptance condition |
| --- | --- | --- | --- | --- |
| 1 | A disconnected user can create and send before learning setup is incomplete. | Native creation offers `ovrcr operator login chatgpt`; the submitted request produces “sign in to the operator provider first.” Chat displays no actionable sign-in control. | Show provider connection status before sending; provide a Connect action and keep the request ready to submit after login. | A new signed-out user can connect and send their retained request through an obvious path without searching docs or reconstructing the request. |
| 1 | Users must understand which workspace a saved chat still targets. | Context is retained per chat, shown as “Managing … / #1 run 1,” and expanded details contain more identities. There is no dedicated target picker in the inspected UI. | Make the target caption actionable: choose project/workspace/session or explicitly use global context; explain that changes affect the next message. Keep submitted targets immutable. | Navigate elsewhere, reopen an old chat, and identify/change its next-message target before sending. |
| 1 | “Quick message” and `[+]` do not say that sending starts another conversation. | Native modal title says Quick message; keymap description, available through menus, explains new-conversation behavior. Ctrl+N takes a different creation route. | Label the modal “New conversation” or “Quick message · new chat,” and clarify how to reply to the current conversation. Keep defaults as the fast path. | A user can predict whether sending creates a chat or replies to the selected one. |
| 2 | Finding the right conversation becomes difficult as the list grows. | Sidebar clips first-prompt titles; only five rows can show; source orders IDs rather than recent activity. No dedicated Operator search, rename, pin or grouping was found in the Operator controls/protocol. | Add conversation rename and a searchable “All conversations” picker first. Show full title and target in that picker; consider recent activity ordering without moving rows while the user selects. | Two chats with similar first prompts can be distinguished, renamed and found after they leave the visible five rows. |
| 2 | First use gives little help about what to ask. | The manual creation flow asks for provider/model before a task; the new chat transcript is blank. | Add a short capability statement and a few selectable starters: list sessions needing attention, explain the current workspace, start a task. Explain that requested shell/CLI actions can execute directly. | A first-time user can choose a useful request and understands its execution implications. |
| 2 | Recovery exposes machinery rather than a clear next step. | Native close confirmation includes conversation/session/run numbers and generic Confirm; docs require CLI acknowledgement for uncertain stops. Stop cannot guarantee rollback. | Put plain action/outcome wording first: “Stop and archive conversation,” “History will be kept,” and an appropriate recovery action. Keep technical IDs in details. Preserve independent stop verification. | Users can distinguish Stop, Archive and Restore, and can tell whether another instruction is safe to send. |
| 2 | Useful controls disappear into focus-dependent shortcuts. | Empty composer footer shows only Newline and Browse. New chat, Chats and transcript navigation are largely in keyboard menus; narrow chat hides the sidebar without showing a Chats control in that footer. | Add compact visible New chat / Chats actions and a consistent focus cue. Surface the next relevant recovery action beside an error. | A mouse-first user can switch chats, start a new one and recover from an error without memorizing Ctrl+L/Ctrl+N. |
| 3 | Reading and reusing answers lacks dedicated chat controls. | No Operator-specific message Copy, transcript Export, Find-in-chat, edit/resend or retry-last-message action was found. Existing terminal History/Copy should not be assumed to cover native chat. | Start with Copy message and an explicit reuse-failed-request action that fills the draft without automatically replaying commands. Add find-in-chat when long histories warrant it. | Users can copy a response and reuse failed input through the chat UI; an interrupted command never replays automatically. |
| 3 | Long-running and long-history chats provide limited orientation. | Activity is inline and scrolls away; history uses paging; no dedicated jump-to-latest, context-budget display or compact-and-continue action was found. | Offer “Latest” when away from the tail; show a context-limit warning with a clear New conversation path. Add a compact elapsed-work hint if users cannot judge ongoing work. | A reader can return to the current result and understands how to continue when a conversation reaches its limit. |

The final two rows are proposed enhancements, not observed runtime failures. Search, rename, copy and target selection are assessed against the dedicated Operator UI and protocol, not every possible shell workaround.

## Evidence and limits

- `rtk proxy just gui` built and launched the app successfully from the reviewed checkout.
- Native actions exercised: entry through `o`, manual chat creation, first-message submit while signed out, multiline Quick message draft, dismissal, close confirmation/cancel, and font zoom into a 98-column full-width chat.
- Retained screenshots: [Quick message](03-quick-message.jpg), [close confirmation](04-close-confirmation.jpg), [wide chat at larger text](05-larger-text.jpg), [98-column chat](06-narrow-chat.jpg).
- AX evidence is adjacent to each screenshot. Captures 03–05 contain incremental AX snapshots; 06 contains a full AX tree. A subsequent click reported `noWindowsAvailable`; reconnecting restored inspection, but typing remained unchanged. Closing the native close control succeeded. This tool interruption is not attributed to an Operator defect.
- Startup emitted a missing Bridge startup-assets notice but continued into the dashboard. Optional Claude/Codex hook installs were skipped. No installation repair was performed.
- The signed-out request exercised durable user-message/error display; no live assistant response or tool execution was evaluated. Streaming/tool/concurrency behavior in the inventory is source-backed and has prior repository acceptance evidence, not a fresh live-provider pass.
- No new tests were run: this was a read-only product review. Existing test source was consulted, without claiming it passed today.
- Screen-reader usability, clipboard delivery, real account login, more-than-five-chat navigation, archive restoration, crash recovery, 60×16 behavior and Linux rendering remain untested in this pass.
- The close control ended the launcher with exit code 0. All recorded fixture PIDs and process groups were absent afterward; the temporary root/socket were removed. See [process inventory](processes.json) and [cleanup](cleanup.json).

## Recommended first slice

Improve signed-out onboarding, make the next-message target explicit and changeable, and clarify that Quick message creates a new chat. These changes improve the first successful task before adding conversation-management features. Follow with searchable/renameable conversations and clearer Stop/Archive/recovery language. No implementation or tracker changes were made.
