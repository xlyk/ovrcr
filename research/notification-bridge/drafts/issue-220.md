## Problem Statement

On macOS, OVRCR's alerts are attributed to Script Editor rather than OVRCR, and clicking a banner cannot take the user to the session that needs attention. Notification submission can succeed without a visible banner, while the Dashboard cannot distinguish missing Bridge installation from denied native permission. Users also need a clear privacy boundary: a conversation-derived session title suitable for the Dashboard is not automatically suitable for a desktop or lock-screen notification.

Users need OVRCR-branded response-ready and input-needed banners with safe navigation to the correct session, without adding another session owner or changing which agent events are eligible for alerts.

## Solution

Provide the Bridge: a small signed, Dock-less macOS app with OVRCR's own stable bundle identity. The Dashboard decides when an alert is eligible and asks the Bridge to display it. A valid click goes through the Server to the active Dashboard, immediately selects the correct session, lands in Browse, and raises the terminal. It never marks reviewed, submits input, or launches a process.

Keep conversation content out of banners. Let macOS manage banner sound and delivered notification history. Make unavailable installation or permission actionable without interrupting ongoing work. Preserve Linux behavior and the existing single-Server, single-active-Dashboard and fifty-live-session contracts.

## User Stories

1. As an OVRCR user on macOS, I want alerts attributed to OVRCR rather than Script Editor, so that I recognize their source and manage the right application's notification settings.
2. As an OVRCR user, I want a response-ready banner for an eligible managed root response, so that I know there is a response to review without interpreting completion as task success.
3. As an OVRCR user, I want an input-needed banner for each newly observed eligible Input request, so that I know when an agent needs my answer.
4. As an OVRCR user, I want Ready and Input request alerts to remain independent, so that one does not hide the other when both occur in the same cycle.
5. As an OVRCR user, I want each eligible response or request alerted at most once, so that duplicate reporting does not produce duplicate interruptions.
6. As an OVRCR user, I want eligible alerts even for a selected or visible session, so that visibility does not silently suppress my chosen notification behavior.
7. As an OVRCR user, I want attach, reconnect and later enablement not to replay already-consumed observations, so that old work does not look like a new event.
8. As an OVRCR user, I want pending Ready alerts canceled when their reporting or activity is no longer eligible, so that an obsolete completion is not newly submitted.
9. As an OVRCR user, I want pending Input request alerts canceled when their request closes or binding is replaced, so that answered or obsolete requests are not newly submitted.
10. As an OVRCR user, I want the banner title to distinguish response-ready from input-needed, so that I understand the kind of attention required.
11. As an OVRCR user, I want the subtitle to use my manual title or the original session name, so that I recognize the session without exposing a generated conversation subject.
12. As an OVRCR user, I want project, workspace, terminal identity and session ID in the banner body, so that similarly named sessions remain distinguishable.
13. As an OVRCR user, I want prompts, responses, answers and generated conversation subjects excluded from banners, so that private conversation content does not appear on the desktop or lock screen.
14. As an OVRCR user, I want notification text to remain bounded and safe when names contain unusual characters, so that session labels cannot inject control text or change the meaning of the banner.
15. As an OVRCR user, I want a valid banner click to immediately select its session through the active Dashboard, so that I can follow an alert without another navigation confirmation.
16. As an OVRCR user, I want a click to focus an existing pane containing the session or select it through normal pane navigation, so that the Bridge does not create another pane owner or duplicate the session.
17. As an OVRCR user, I want a click to land in Browse, so that entering terminal input remains an explicit action.
18. As an OVRCR user, I want a click to dismiss transient dialogs and the palette without submitting them, so that a navigation action never confirms an unrelated operation.
19. As an OVRCR user, I want unsent Dashboard drafts discarded and History/Copy released during an immediate switch, so that transient UI from another session does not remain attached to the new target.
20. As an OVRCR user, I want already-submitted operations to remain bound to their original targets, so that a later click cannot redirect their results or side effects.
21. As an OVRCR user, I want previously queued input never redirected to the clicked session, so that switching panes cannot send unintended commands.
22. As an OVRCR user, I want clicking an alert not to mark a response reviewed or answer an Input request, so that navigation remains distinct from acknowledgement.
23. As an OVRCR user, I want clicking an alert not to launch, recover, reopen or restart anything, so that a historical banner cannot execute work.
24. As an OVRCR user, I want a click with no active Dashboard or no target to do nothing, so that the Bridge does not open a second Dashboard or invent a destination.
25. As an OVRCR user, I want clicks fenced to the original Server lifetime and session run, so that a banner from old work cannot select a reopened run or a replacement Server.
26. As an OVRCR user, I want archived targets ignored, so that historical banners do not restore archived work.
27. As an OVRCR user, I want process exit alone not to invalidate otherwise valid navigation, so that I can still inspect the original session without starting a new process.
28. As an OVRCR user in iTerm, I want an authorized integration to select the exact existing iTerm session, so that a click reaches the terminal hosting the active Dashboard.
29. As an OVRCR user, I want parent-terminal activation when exact iTerm selection is unavailable, so that clicking still raises my terminal without claiming exact-window precision.
30. As an OVRCR user, I want terminal-control setup to be explicit and separate from notification permission, so that ordinary banner clicks do not unexpectedly initiate another permission flow.
31. As an OVRCR user on macOS, I want sound requested as part of the banner only when both saved alert flags are on, so that sound follows native notification policy without duplicate player playback.
32. As an OVRCR user on macOS, I want to choose an original bundled short tone or the system default sound in Dashboard settings, so that I can choose the agreed sound without a separate Bridge settings window.
33. As an OVRCR user with an existing sound-only macOS configuration, I want my saved flags preserved and the new dependency explained, so that an upgrade neither exposes banners without consent nor discards my preference.
34. As an OVRCR user on macOS, I want the sound toggle never to enable banners and disabling banners to retain the saved sound preference silently, so that the two saved preferences remain under my control even though effective sound requires both.
35. As an OVRCR user, I want notification permission requested when notifications are enabled, so that missing authorization is discovered before an eligible alert is lost.
36. As an OVRCR user with denied permission, I want an unavailable footer and an explicit action to open System Settings with instructions for Notifications → Bridge, so that I can recover without a modal interrupting my work or Settings opening automatically.
37. As an OVRCR user with no installed Bridge, I want installation guidance rather than irrelevant permission guidance or a Script Editor fallback, so that the recovery path matches the actual failure.
38. As an OVRCR user, I want a stable signed Bridge installation unaffected by ordinary CLI rebuilds, so that development does not repeatedly replace the application identity used for permissions.
39. As an OVRCR user, I want the Dashboard to start the Bridge as needed and keep it running for notification delivery without a Dock icon, so that notification handling is available without another visible application to manage.
40. As an OVRCR user, I want slow, missing or failing delivery to leave terminal input, rendering, detach and reporting responsive, so that native notifications cannot stall my sessions.
41. As an OVRCR user, I want best-effort delivery without retries or claimed proof of visibility/audibility, so that OVRCR does not turn OS suppression into repeated alerts or misleading success claims.
42. As an OVRCR user, I want delivered banners left to macOS and my own history management, so that the first slice does not add an unexpected notification retraction or replacement policy.
43. As an OVRCR user, I want currently eligible Claude, Codex, Pi and Oh My Pi alerts supported without waiting for Grok parity, so that an unrelated provider gap does not block the Bridge.
44. As an OVRCR user on Linux, I want the existing notification and independent sound behavior unchanged, so that a macOS improvement does not alter my desktop workflow.
45. As an OVRCR user with up to fifty live sessions, I want bounded alert work and unchanged runtime capacity, so that notification delivery does not create unbounded queues or competing process ownership.

## Implementation Decisions

- Preserve the existing ownership split: shared reporting defines eligibility; the Dashboard makes alert decisions; the Bridge performs native display and terminal activation; the Server owns sessions, processes and the active Dashboard. The Bridge neither interprets provider frames nor filters providers independently.
- Extend the existing Dashboard delivery boundary for the macOS host rather than creating a second alert engine. Retain response/request identity deduplication, attach/reconnect baselines, visible-session behavior, bounded work, nonblocking delivery and cancellation of eligible pending/in-flight work. Preserve default-off preferences, atomic settings-save failure behavior and explicit mark-reviewed semantics.
- Provide one small signed macOS application bundle at a stable path with a stable OVRCR identity and no Dock icon or settings window. Ordinary CLI development runs do not replace the Bridge. The Dashboard starts it as needed and leaves it running for notification delivery. This is separate from the existing disposable GUI test helper.
- The banner title distinguishes response-ready and input-needed. Its subtitle is the manual title when present, otherwise the original session name. Its body carries project/workspace/terminal identity and session ID. Never use a generated conversation subject as the notification name, and never transmit prompts, responses or answers to the native display boundary. Preserve existing identity sanitation and bounds.
- Extend the shared Server request/event contract with navigation to the active Dashboard. This is not the existing terminal-attach Select request and must not claim another Dashboard seat, bypass the acknowledged view handshake, or add a private Bridge-to-Dashboard channel. Keep the transport synchronous, bounded and consistent with the existing sole-writer and owner-verification mechanisms.
- A click is tied to its originating Server lifetime, session identity and run. Revalidate the target when routing and applying it. Reopen, Server restart, archive, missing target and absent active Dashboard make it a no-op. A draining or replaced Dashboard must not receive a stale-owner operation. Process exit alone does not prohibit navigation. No click may cause process launch or display-triggered recovery.
- Apply a valid click immediately through ordinary pane selection: focus the pane already containing the session, otherwise select it in the focused pane. Land in Browse; dismiss dialogs/palette without submitting; discard unsent drafts; release History/Copy through normal retarget cleanup. Already-submitted requests keep their original targets, stale capture/clipboard completions cannot cross the switch, and old queued input cannot reach the new target. A click does not review or answer anything.
- Terminal activation targets the terminal hosting the active Dashboard, not a stale remembered terminal. Use exact existing-iTerm-session selection only when the integration is available and explicitly authorized. Otherwise activate the parent terminal application, with its known multiple-window limitation. Ordinary clicks must not deliberately start terminal-control authorization. Do not create iTerm sessions, manipulate tabs, send input or read screen content.
- On macOS, effective sound requires both desktop-notification and sound flags. Request at most one sound on the banner and remove separate player playback for this feature. Preserve saved flags even when sound is ineffective. Explain the dependency in the Dashboard; the sound toggle never enables banners, and disabling banners does not clear the sound flag. Keep a short Dashboard selector for original bundled tones and system default, defaulting to system default; off remains the existing sound toggle. Linux sound is unaffected.
- Notification permission is distinct from terminal-control permission. Request notification permission when notifications are enabled. Denial yields an unavailable footer and an explicit recovery action to open System Settings with manual Notifications → Bridge instructions; missing installation yields installation guidance. Do not open Settings automatically, interrupt with a denial modal, or fall back to Script Editor notifications. Permission and host failures must not alter reporting or process state.
- Keep best-effort submission without retries. Native policy, including Focus, permission and per-application sound settings, may suppress visible or audible delivery; successful submission is not proof of either. Leave delivered history under OS/user control rather than adding retraction, replacement or aggregation. Preserve cancellation of work not yet delivered when preferences, lifecycle or reporting make it ineligible.
- Preserve the fifty-live-session limit, one Server owner, one active Dashboard, retained-session identity, run fencing and existing persistence authorities. No new conversation/output store or session database migration is required by the product contract. Reuse the Dashboard settings store for the sound choice and related preferences.
- Native signing/update behavior, Bridge compatibility with changing CLI/Server protocols, precise permission/settings behavior, original bundled sound provenance and supported native sound requirements and exact iTerm control permissions remain verification gates. Verify these facts before implementing a dependent design; report a conflict rather than substituting a different UX or weakening the privacy/ownership contract. The native language, precise bundle identifier/path and IPC encoding are not newly selected by this spec.

## Testing Decisions

- **Primary automated seam:** reuse the existing real-application desktop-alert integration fixture. Drive managed provider observations into an isolated live Server, run the production Dashboard/event loop under a real PTY, observe outbound host deliveries, inject clicks through the production Server-facing entry point, and assert visible Dashboard outcomes. Prefer this combined application path over independent mock-only tests of each new helper.
- **Only new test-double boundary:** where deterministic headless testing needs it, substitute the native Bridge host at the existing delivery boundary. Let that substitute record sanitized payloads, model missing/denied/failing/slow responses and supply click callbacks through the real navigation entry point. The production constructors, queueing, writer, owner checks, Dashboard dispatch and view handshake remain exercised; do not introduce a second reporting or Dashboard-selection implementation for tests.
- **External-behavior assertions:** an accepted Ready and Input request each submit once; duplicates, child/stale observations and reconnect/enable baselines do not add calls; both lanes work for selected/visible/split sessions; invalidation cancels its own pending lane. Verify private sentinel subjects/prompts/answers never reach the host, and manual-title/original-name fallback produces the agreed title/subtitle/body.
- **Navigation assertions:** a valid click selects the expected pane/session and visibly lands in Browse while Unread/request state stays unchanged. Cover active input, dialogs, unsent drafts, History/Copy, queued input, late capture/clipboard completions, already-submitted operations, missing/archived/exited targets, reopened runs, Server restart, Dashboard detach/reattach/replacement and stale-owner cleanup. Assert no new process or automatic recovery is spawned, and no old input reaches the target.
- **Preferences and failure assertions:** cover all four notification/sound flag combinations on macOS, persisted sound-only configuration, original-tone/system-default choice, saved settings after reconnect, and failed saves leaving preferences unchanged. Test denied permission versus missing installation guidance, explicit Settings action, no automatic Settings opening or Script Editor fallback, unavailable/unconfigured iTerm control, and continued input/rendering/detach with a blocked or failing host. Keep Linux independent notification/sound assertions intact; change macOS expectations only for the intentional banner-sound contract.
- **Meaningful unit coverage:** retain focused tests for identity validity, sanitized notification fields, settings semantics and protocol validation within their owning modules, alongside the real-application integration cases. Helpers/mocks alone are insufficient acceptance.
- **Prior art:** the existing real-PTY desktop-alert suite already proves host-call counts, privacy sentinels, managed Ready/Input delivery, visible panes, no replay, host failure and nonblocking input/detach. The shared isolated live-server fixture provides real sockets/config/workspaces and task-owned cleanup. Dashboard retarget/view-handshake tests and real-GUI settings persistence tests provide precedent for navigation, capture cancellation and saved preferences.
- **Native macOS seam:** run the actual signed Bridge and reviewed Dashboard checkout against disposable resources through a capable computer-use harness. Retain screenshots and relevant accessibility evidence proving OVRCR sender identity, both banner kinds, banner layout, real click-to-focus/Browse behavior, permission/recovery UX, prior-authorized exact iTerm selection and fallback activation. Separately verify the chosen sounds, stable identity through ordinary CLI rebuilds, restart/reopen stale-click behavior and absence of a Dock icon. Headless payload recordings cannot prove native banners, permission identity, exact terminal activation or audibility.
- **Regression gates:** use the owning TUI library and root TUI/server-lifecycle integration suites while developing; before feature acceptance, run workspace all-target/all-feature tests, all-target/all-feature checking, formatting and strict clippy plus relevant GUI coverage. Required Linux regression/capacity/memory gates retain their existing assertions. Confirm filters execute tests and distinguish native macOS, automated Linux and any unavailable native checks; skipped/unrun checks are not passes. Do not run these feature suites merely to publish this prose spec.
- Every live/native test gets private configuration, sockets and workspaces. Native acceptance must use a task-owned Bridge installation/identity or explicit authorization for any shared native permission state; do not replace the user's stable Bridge or alter live-session configuration as a test shortcut. Stop/remove only proven task-owned resources and retain required evidence. Preserve fifty-session capacity and bounded-work coverage.

## Out of Scope

- Implementing reporting parity or inventing readiness/input surfaces for Grok, Hermes or unsupported Claude/Codex events.
- A second Dashboard, Server, Reporter, session/pane owner, terminal-per-session application or conversation/output store.
- Bridge-driven server restart, process management, automatic recovery, Reopen, review acknowledgement, Input answers or arbitrary terminal input.
- iTerm tab creation, color/badge changes, screen reading or input sending; unrelated direct-iTerm features.
- A Dock icon, Bridge settings window, arbitrary sound-file paths, Linux sound-choice changes, or notification-policy bypass.
- macOS sound-only playback, delivered-banner retraction/replacement/aggregation, retries or guaranteed visible/audible delivery.
- Changes to the source brainstorm or original checkout, application implementation, commits, pushes, PRs or merges as part of spec publication.
