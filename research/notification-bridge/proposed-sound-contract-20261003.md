## Current behavior and settings authority

`ovrcr_protocol::settings::Settings` currently declares only `desktop_notifications` and `ready_sound` for alerts, both defaulting false. There is no shipped sound selector, stored Glass enum or choice migration to perform. `dashboard/desktop.rs::alert_channels` currently treats those flags independently; its macOS `sound_command` invokes `afplay /System/Library/Sounds/Glass.aiff`. Linux uses independent `notify-send` and `paplay` paths. ADR 0006 and #224 specify future banner-based macOS sound and a future Glass/default selector; those requirements have not been implemented.

Use the existing ADR 0007 settings authority: typed value in `ovrcr-protocol`, parsing/report rows in `ovrcr-runtime::settings`, its in-place validated writer, Server snapshots, Dashboard editor and CLI setting operations. The Dashboard does not parse a second file and the Bridge owns no settings window or persistence. Update shared constructors/callers and the ordinary wire version together when a new typed field is implemented; the historical prototype wire is not the current release contract.

## Apple source facts and limits

Apple documents Linear PCM, IMA/ADPCM, µLaw and aLaw custom alert audio, packaged as AIFF, WAV or CAF. Duration must be **less than 30 seconds**; a sound over 30 seconds is documented to use the system default. Include a predefined set in the application bundle before delivery. Mono 48 kHz, signed 16-bit PCM WAV candidates satisfy the documented codec/container category; their headers and durations still require static validation and later actual native acceptance. The source does not promise a particular sample-rate/loudness experience on every supported machine. [Custom sound requirements](https://developer.apple.com/documentation/usernotifications/unnotificationsound)

`UNNotificationSound(named:)` accepts a **filename**, searching the app container's `Library/Sounds`, then shared group containers' `Library/Sounds`, then the main bundle, and selecting the first match. It is not a validated arbitrary-path API and constructing this nonfailable object does not prove the intended bytes exist, decode or play. App-specific versioned filenames reduce accidental collisions; they do not override the documented search order. Do not populate alternate sound containers for this release. A known conflicting higher-precedence resource must be reported rather than removed from user data or described as the signed bundled tone. [Named sound lookup](https://developer.apple.com/documentation/usernotifications/unnotificationsound/init(named:))

`UNNotificationSound.default` represents the OS's default notification sound; it does not promise a fixed asset, tone identity, pitch or duration. It needs no bundled audio file. Both default and the ordinary named-sound facility are available on macOS from 10.14 in the current documentation/SDK. Use the ordinary sound APIs, not ringtone or critical-alert variants. [Default sound](https://developer.apple.com/documentation/usernotifications/unnotificationsound/default)

Assign the sound to `UNMutableNotificationContent.sound` for native banner delivery. When the application lacks sound authorization, the system ignores that property. Permission status, submission success, foreground delegate activity, a visible banner and audible sound are distinct evidence; silence never authorizes an independent player, retry or policy bypass. [Content sound property](https://developer.apple.com/documentation/usernotifications/unmutablenotificationcontent/sound)

The installed `UNNotificationSound.h` agrees on default semantics, named container/bundle lookup and macOS availability. Its named factory returns a sound object without a file-validation error result. The fetched references do not specify every missing/unreadable/corrupt-file fallback on macOS; the application must reject a known invalid selected resource before requesting that sound rather than relying on undocumented fallback behavior.

## Proposed selection, persistence and resource contract

Propose one string setting, **`ready_sound_choice`**, with these exact stable values. Keep the persisted IDs independent of presentation labels and resource version names; no arbitrary file path is accepted.

| Persisted ID | Dashboard label | Native sound request | Candidate encoding / duration |
| --- | --- | --- | --- |
| `default` | System default | `UNNotificationSound.default` | OS-controlled; no shipped asset |
| `tap` | Tap | named `ovrcr-tap-v1.wav` | Mono 48,000 Hz, signed 16-bit little-endian PCM WAV; 0.22 s |
| `chime` | Chime | named `ovrcr-chime-v1.wav` | Same encoding; 0.84 s |
| `rise` | Rise | named `ovrcr-rise-v1.wav` | Same encoding; 0.64 s |

**Recommended absent-setting default: `default`.** This chooses the supported system facility without automatically selecting a newly introduced custom preference. Both consent flags still default false. Reading an absent choice resolves the effective value without writing a new key or changing either flag. Explicitly choosing a tone writes only the selector through the existing settings path; `S` remains the sound on/off toggle. A selector change itself neither enables sound nor enables banners, requests permission, replays old alerts or automatically previews audio.

Persist an explicit valid choice through restart, reconnect, CLI changes and unrelated settings edits. A save refusal leaves the active choice/flags unchanged until a successful Server snapshot arrives. Unknown or wrong-type explicit values, including a hypothetical manually written `glass`, retain their raw document text and produce the existing per-setting diagnostic. Do not invent a shipped Glass-field migration, rewrite a value as `default`, drop an unrecognized key, or expand consent. The loader can retain its normal effective-default behavior, but **proposed delivery behavior** suppresses sound while a selector-specific finding remains, with actionable sound-unavailable status; this prevents a diagnostic default from silently substituting for an explicit unsupported choice. Other valid settings and banner eligibility remain usable.

Old documents containing only the two flags require preservation, not a conversion:

| Saved desktop / sound | Effective macOS behavior | Saved state |
| --- | --- | --- |
| off / off | No banner or sound | Preserve both flags and any selector |
| on / off | Banner with `sound=nil` | Preserve sound preference and selector |
| off / on | No banner or sound; explain sound requires notifications | Keep the sound-only flags exactly as saved |
| on / on | One native banner with the selected sound, subject to OS authorization/policy | Preserve flags and choice |

Apply the same rule to Ready and Input alerts; retain shared eligibility, deduplication, no replay and cancellation of pending/in-flight work. A settings change applies before a not-yet-submitted sound; it never replays an already consumed alert or retracts OS-managed delivered history. Disabling `N` leaves the saved sound flag/choice unchanged; enabling `S` does not enable `N`. Show the dependency in macOS help/editor text without a modal or automatic Settings opening.

On Linux, keep the existing independent flags and `notify-send`/`paplay` behavior, including sound-only operation. The new selector may travel in the shared settings snapshot and remain saved, but it has no Linux playback effect or Linux chooser in this slice. Do not replace Linux sound resources or weaken Linux regression assertions.

Package all three original WAV files as regular `Contents/Resources/ovrcr-*-v1.wav` bundle resources. No symlink, Apple audio extraction/copy, app-group entitlement, additional audio dependency or runtime synthesis is required. Retain mathematical generator source, its deterministic parameters, the repository MIT notice, measured encoding/duration and a per-file SHA-256 manifest. Generation must take no sampled/input audio; byte-identical regeneration and read-only decode checks verify provenance/structure, not pleasantness or audibility. The worker demonstrated reproducibility on its recorded Python/macOS environment; platform math differences prevent assuming identical generated bytes everywhere. Signed release packaging must preserve these exact approved bytes and license notice. Updates that change a tone's bytes use a new resource version and manifest while retaining the choice ID; never change a persisted ID's meaning to a different tone without an intentional contract change.

Before requesting a custom sound, verify its allowlisted bundled resource exists, is a regular readable file inside the bundle, matches the approved hash/encoding and stays below the duration bound. If it is missing, corrupt, unreadable, changed or a known competing lookup resource is present, return a typed sound-unavailable reason. **Proposed failure behavior:** keep the saved choice and flags, submit an otherwise eligible banner silently (`sound=nil`), and expose the sound failure through the existing Dashboard unavailable/footer path. Do not substitute system default, another custom tone, `afplay`, independent audio or an automatic retry. The diagnostic source and production path must state whether a silent banner was submitted; a sound-object constructor is not a resource check or acknowledgement of audible delivery.
