## RESULT: FAILED for ~/.pi — read this before trusting anything else here

`find ~/.pi -newer marker-before` printed one path:

That is the DIRECTORY's own mtime (2026-09-14 00:14:09, marker 2026-09-13 23:59:16).
`find ~/.pi/agent -mindepth 1 -newer marker-before` printed NOTHING: every entry inside
still carries its pre-run mtime --

    sessions/         Sep  9 17:15

    npm/              Aug 27 21:42

A directory mtime moves when an entry is created or removed, so a file was created inside
~/.pi/agent and removed again at 00:14:09. No entry persisted and no existing file was
modified.

CAUSE — mine, not OVRCR's. While characterising the failed --version probe (Defect 1) I
timed and sampled the real Pi binary against the REAL home rather than the fixture home:

    /usr/bin/time -p /Users/xlyk/.local/bin/pi --version          (~00:11-00:12)
    cd /tmp && /Users/xlyk/.local/bin/pi --version & sample $P    (~00:14)

The last of those matches the directory mtime. Starting pi with HOME=~ let it create and
remove a transient file in its own agent directory. That breaks the runbook's hard rule
"Nothing is written to ~/.pi". It should have been measured only as
`env HOME="$ROOT/home" ... pi --version`, which is how the other measurements in
05a-pi-probe-failure.txt were taken.

Scope of the breach: one transient entry in ~/.pi/agent, created and removed by Pi itself.
No credential, session, setting or trust file was written, changed or deleted; none of
their mtimes moved. Nothing was printed from any of them. The fixture run itself
(everything from 04-launch-shape.txt onward) used HOME=$ROOT/home throughout and is not
implicated.
