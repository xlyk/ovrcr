**Substantiated findings**

1. **[Blocker] Dashboard model controls have no source-safe discovery owner.**  
   **Scenario:** The session dialog must show verified model choices before Start. The observed harness discovery lives inside `ServerState::delegation_capabilities`, after `delegation_auth(auth)?` and `reject_assigned_input(auth.session)?` (`crates/ovrcr-runtime/src/server/delegation.rs:799-850`). The plan correctly says not to expose that authority, but supplies no alternative request or shared read-only path. `AgentEntry` carries only `name`, `argv`, and `source` (`crates/ovrcr-tui/src/dashboard/agents.rs:32-39`), so the TUI cannot obtain models without either calling delegation code or guessing from the harness name—both forbidden by Plan §1–2 and Design “Harness, model and initial prompt.” The same source discovery match has no OMP arm and falls through to refusal; `src/report/omp.rs:1-28` is reporting-only.  
   **Evidence:** Plan §1–2; Design “Harness, model and initial prompt”; `crates/ovrcr-runtime/src/server/delegation.rs:799-850`; `crates/ovrcr-tui/src/dashboard/agents.rs:32-39`; `src/report/omp.rs:1-28`.  
   **Smallest correction:** Define the concrete Server read-only capability request/catalog (or extend the settings report) keyed by exact launch configuration, usable without delegation auth or a forged session. Make Step 2 wire changes conditional on Step 1’s exit, and return “unavailable” for OMP until a real model/prompt mechanism is proved.

2. **[High] The Branch picker cannot implement “registered-only” from the current hierarchy shape.**  
   **Scenario:** A retained session can outlive its registry workspace. `snapshot_from_state` deliberately synthesizes a `WorkspaceSummary` for it with `name = git::UNAVAILABLE_CHECKOUT` and `root = false` (`crates/ovrcr-runtime/src/server/mod.rs:3101-3107`). The Dashboard receives only `WorkspaceSummary` fields (`crates/ovrcr-protocol/src/wire.rs:429-435`), which have no `registered` discriminator. Iterating `hierarchy.projects[].workspaces` would therefore offer an unregistered retained-session row; filtering by name would also hide a registered workspace whose checkout is unavailable. This contradicts Design “Session dialog” registered-only filtering and Plan §3’s “Build the Branch picker from registered workspace identities.”  
   **Evidence:** Plan §3; Design “Session dialog”; `crates/ovrcr-runtime/src/server/mod.rs:3101-3107`; `crates/ovrcr-protocol/src/wire.rs:429-435`.  
   **Smallest correction:** Add an explicit registration/identity discriminator to the picker data, or have the Server publish a dedicated registered-workspace list. Do not infer registration from branch text, path, or `UNAVAILABLE_CHECKOUT`. Add a retained-session synthetic-row case.

3. **[High] “Use the returned workspace ID” is unsupported for child branch creation.**  
   **Scenario:** The child uses the standalone `CreateWorkspace` job. On success, `lifecycle.rs` returns `LifecycleOutcome::Succeeded`, which has no workspace identity; only `CreatedSession` carries a session summary (`crates/ovrcr-runtime/src/server/lifecycle.rs:170-175`; `crates/ovrcr-protocol/src/wire.rs:504-507`). If the Dashboard follows Plan §3 literally, it has no returned ID and may fall back to provisional branch text—exactly what the design forbids.  
   **Evidence:** Plan §3; Design “Create branch dialog”; `crates/ovrcr-runtime/src/server/lifecycle.rs:170-175`; `crates/ovrcr-protocol/src/wire.rs:200-203, 504-507`.  
   **Smallest correction:** Retain the submitted `id` from `Request::CreateWorkspace` in the Dashboard’s pending child state and select only that ID after the hierarchy refresh. Alternatively extend `LifecycleOutcome` with `WorkspaceCreated { project, id }` and update constructors/tests.

4. **[High] Capability binding and native argv composition for overrides are undefined.**  
   **Scenario:** `apply_overrides` matches by `AgentEntry.name` and replaces `argv`, leaving an entry that still appears as “claude” even when the executable is an arbitrary wrapper (`crates/ovrcr-tui/src/dashboard/agents.rs:98-110`). Plan §1–2 correctly says a display name does not prove safe model/prompt support, but no step defines how the Server knows the capability of that override. Separately, managed launches wrap native argv as `[launcher, agent, run, name, --, native]`, and the wrapper `--` is explicitly not a prompt separator (`agents.rs:55-70`); auto-trust is inserted before a native `--` prompt separator (`crates/ovrcr-protocol/src/auto_trust.rs:50-63`). Appending a structured prompt/model to the wrong layer can change native parsing or silently add flags.  
   **Evidence:** Plan §1–2; Design “Harness, model and initial prompt”; `crates/ovrcr-tui/src/dashboard/agents.rs:55-70, 98-110`; `crates/ovrcr-protocol/src/auto_trust.rs:50-63`.  
   **Smallest correction:** Define capability identity from exact executable, argv shape, and configuration source; mark overridden/unknown launches unsupported and inject no model/prompt. Define per-provider native prompt/model placement relative to auto-trust and the native `--`, with tests for leading-dash prompts and conflicting configured flags.

5. **[Medium] Pending initial-prompt ownership across Dashboard reconnect lacks a stable correlation anchor.**  
   **Scenario:** Plan §2 promises server-owned pending prompt text with a run identity that survives Dashboard reconnect. Current lifecycle completion is correlated by `client_token`, documented as the request ID accepted on that Dashboard connection (`crates/ovrcr-protocol/src/wire.rs:543-545`). `Lifecycle` exposes one in-flight token and no read/reconcile query (`crates/ovrcr-runtime/src/server/lifecycle.rs:75-101`), while the Dashboard’s failed-launch request is local to the palette (`crates/ovrcr-tui/src/dashboard/palette.rs:150-151`). A reconnect cannot recover the pending prompt or correlate the accepted job; a restart cannot truthfully report its fate.  
   **Evidence:** Plan §2; Design “Harness, model and initial prompt”; `crates/ovrcr-protocol/src/wire.rs:543-545`; `crates/ovrcr-runtime/src/server/lifecycle.rs:75-101`; `crates/ovrcr-tui/src/dashboard/palette.rs:150-151`.  
   **Smallest correction:** Add a server-owned pending-launch record with a stable launch/session-run ID and a bounded read/reconcile request, or narrow retention to the same Dashboard process and remove the server-owned reconnect claim. Preserve the design’s no-automatic-replay rule.

**Proof gaps, not counted as findings**

Step 1 is still an unexecuted research gate: there is no installed-launcher evidence for OMP model discovery, initial-prompt delivery, or native trust behavior; Claude/Codex/Pi discovery contracts are delegation-specific and unproven for Dashboard use. Exact auto-trust/prompt separator behavior and Pi/OMP extension `-e` insertion also remain unverified. No CUA, layout, provider delivery, or cleanup evidence was run. The plan’s launch-memory schema change for model policy is not specified against the current plain `LaunchChoice` enum (`crates/ovrcr-protocol/src/settings.rs:1518-1524`).

**Plan-quality verdict: NEEDS REVISION.** The design is coherent, but the plan cannot be implemented safely until the discovery route, registered-picker discriminator, workspace-ID source, capability binding, and reconnect correlation are made concrete.
