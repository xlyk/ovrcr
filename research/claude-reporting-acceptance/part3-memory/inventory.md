## Fixture-local child API failure candidate

The narrow candidate is an inline custom subagent whose model is a deliberately nonexistent full-name-shaped value, reinforced by the process-local subagent model override:

```text
CLAUDE_CODE_SUBAGENT_MODEL=claude-ovrcr-child-invalid-2099

--agents '{"ovrcr-child-api-failure":{"description":"Run only when explicitly requested by the Task 8 fixture","prompt":"Return one short response and use no tools.","tools":[],"model":"claude-ovrcr-child-invalid-2099","maxTurns":1}}'
```

The root prompt should explicitly invoke `ovrcr-child-api-failure` once, wait for it to fail, then make the root return a distinct success marker. Do not pass `--agent`; that would run the root as the custom agent. Remove any inherited `CLAUDE_CODE_SUBAGENT_MODEL` before setting the fixture value, and apply this environment only to the one managed invocation. The parent keeps its existing endpoint, valid model, authentication, and account limits.

Exact `/Users/xlyk/.local/share/claude/versions/2.1.268 --help` exposes `--agents <json>` and says it defines custom agents for the invocation. It also exposes the root-only `--agent <agent>` separately. OVRCR's current [eligible launch grammar](../../../src/report/admission.rs#L83) already accepts `--agents` with a following value. The current official [custom subagent reference](https://code.claude.com/docs/en/sub-agents) says CLI-defined agents exist only for the launched session, accept `model`, `tools`, and `maxTurns`, and that `CLAUDE_CODE_SUBAGENT_MODEL` has precedence over both the per-invocation Agent-tool model and the definition's model. The [hook reference](https://code.claude.com/docs/en/hooks) says a subagent hook carries `agent_id` and `agent_type`, and `StopFailure(error=model_not_found)` is the API-error event to target.

This is promising, not certified. The rolling docs allow a full model ID but do not promise that exact 2.1.268 sends an unknown subagent model to the API rather than rejecting it locally. The existing exact-version help does not document subagent model resolution. The retained 2.1.267 [root invalid-model capture](../../../research/claude-reporting-acceptance/native-final/results.md#L27) proves a root `model_not_found`, not a child failure. One native 2.1.268 capture must establish this exact sequence: matching root binding; `SubagentStart` with a unique child `agent_id`; `StopFailure(error=model_not_found)` with that same child identity; no root binding, activity, health, context, usage, cost, or revisions changed by the child callback; then a successful root response on the original binding. If 2.1.268 rejects the inline definition before `SubagentStart`, the candidate fails and the gap remains open.

One-second RSS sampling, charged index bytes, and encoded queue lengths do not prove allocator or kernel high-water.

## Local high-water decision

Do not run the 50-collector raw-record high-water on this busy host. A direct `df -k` check reported only 975,524 KiB available (about 953 MiB). Fifty distinct 32 MiB sources require 1,638,400 KiB (1,600 MiB), already 662,876 KiB beyond available space before build output, indexes, logs, and filesystem overhead.

A single shared 32 MiB source can reduce fixture disk use, as the existing index load shared one transcript, but it does not reduce collector memory: 50 independent pending vectors hold 1,600 MiB of record bytes. Simultaneously reaching the stated 16 MiB charged-index ceiling adds up to another 800 MiB, making 2,400 MiB (2.344 GiB) of stated payload/index ceilings before BTree nodes, vector capacity, JSON expansion, helper/runtime baselines, queues, thread stacks, native processes, and kernel buffers. The existing evidence does not support an additive RSS prediction or show enough headroom on this busy machine. Task 8's deterministic barrier fixture belongs on a preflighted isolated macOS and Linux runner; source review alone leaves the total-memory requirement open.
