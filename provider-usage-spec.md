## Problem Statement

OVRCR users switch between Claude, Codex, and Grok without a shared view of how much provider allowance remains. They must inspect each provider separately and can discover an exhausted limit only after attempting work.

OVRCR's existing conversation tokens, estimated cost, and context occupancy do not answer this question. Those measurements describe individual sessions, not the account allowance shared by several sessions.

## Solution

Show a fixed **Quota left** block at the bottom left of the Dashboard sidebar. Use stacked remaining-allowance bars and numeric percentages for Claude, Codex, and Grok. Show separate **5h** and **7d** rows wherever those windows are actually reported. Grok shows its actual weekly or monthly allowance; do not invent a five-hour window.

Fuller bars mean more allowance remains. Each provider stays identifiable when data is unavailable. Missing, stale, expired, unsupported, and conflicting observations have explicit states rather than fabricated zero or full bars.

Claude uses native quota reports from a managed Claude session and may remain waiting until one reports. Codex uses its documented native account-rate-limits interface. Grok must use a validated, provider-permitted native billing interface with a typed allowance response. No provider login manager or direct Claude OAuth credential reader is included.

The first useful release includes all three providers. An always-unavailable Grok placeholder or a Claude-only release does not satisfy this specification. Agent execution begins with the source-validation gates below and stops with a named blocker if safe collection cannot be established; it must not substitute session metrics or an unapproved credential-reading fallback.

## User Stories

1. As an OVRCR user, I want provider allowance visible at the bottom left of the sidebar, so that I can monitor it without leaving the Dashboard.
2. As an OVRCR user, I want Claude, Codex, and Grok included, so that I can compare all three providers I use.
3. As an OVRCR user, I want bars to show remaining allowance, so that a fuller bar consistently means more room to work.
4. As an OVRCR user, I want numeric percentages beside the bars, so that coarse bar fill does not hide the actual reported value.
5. As a Claude user, I want separate five-hour and seven-day windows, so that I can distinguish short-term limits from weekly allowance.
6. As a Codex user, I want separate five-hour and seven-day windows when reported, so that I can monitor both limits independently.
7. As a Codex user, I want actual window durations and metered buckets preserved, so that a different plan is not mislabelled as five-hour or seven-day allowance.
8. As a Grok user, I want the actual weekly or monthly period shown, so that I do not mistake a billing-period allowance for a five-hour limit.
9. As an OVRCR user, I want missing individual windows distinguished from exhausted windows, so that missing data does not look like zero allowance.
10. As an OVRCR user, I want source usage of zero to produce full remaining allowance, so that explicit zero is not confused with an absent value.
11. As an OVRCR user, I want exhausted and over-limit observations identified clearly, so that display clamping does not conceal the provider's state.
12. As a Claude user, I want OVRCR to reuse my managed session's native quota report, so that OVRCR does not become another OAuth client.
13. As a Claude user, I want a waiting state before a native report arrives, so that OVRCR does not run paid work merely to populate a meter.
14. As an OVRCR user, I want quota source provenance available, so that I know which native session or profile supplied an observation.
15. As an OVRCR user with several sessions, I want shared allowance counted once, so that additional sessions do not inflate usage or duplicate account polling.
16. As an OVRCR user with different logins, I want their observations kept distinct, so that OVRCR does not combine unrelated account allowances.
17. As an OVRCR user, I want old observations fenced after a source change, so that a delayed response cannot overwrite the newly selected source.
18. As an OVRCR user, I want stale data visibly marked, so that a retained percentage is not mistaken for a recent account check.
19. As an OVRCR user, I want the last valid value retained through temporary collection failures, so that a transient outage does not erase useful context.
20. As an OVRCR user, I want authentication failure distinguished from ordinary unavailability, so that I can take the correct action without exposing credentials.
21. As an OVRCR user, I want reset times available in details, so that I can tell when a constrained window is expected to reset.
22. As an OVRCR user, I want a passed reset marked expired or reset due until a new report arrives, so that OVRCR does not invent replenished allowance.
23. As an OVRCR user, I want quota details accessible through the existing Browse menu and palette, so that I can inspect them without relying on a mouse.
24. As an OVRCR user, I want details to show source, window, last observation or check, reset time, and availability reason, so that I can judge the observation's reliability.
25. As an OVRCR user with a narrow sidebar, I want labels and percentages preserved before decorative bars, so that the information remains readable.
26. As an OVRCR user with a short window, I want session navigation preserved, so that the quota block does not make the tree unusable.
27. As an OVRCR user, I want hidden-sidebar behavior preserved, so that hiding the sidebar returns its space to panes without destroying sessions or cached quota.
28. As an OVRCR user, I want the last session row selectable and clickable above the quota block, so that reserved quota space does not corrupt tree hit-testing.
29. As an OVRCR user, I want quota cells excluded from session selection and close-mark hit-testing, so that inspecting usage cannot accidentally operate on a session.
30. As an OVRCR user, I want quota collection isolated from terminal input and output, so that an unavailable provider does not stall my work.
31. As an OVRCR user who detaches and reattaches the Dashboard, I want bounded cached quota restored with its age, so that reattachment does not create duplicate collectors or falsely fresh data.
32. As an OVRCR user with fifty live sessions, I want account reads deduplicated, so that session capacity does not multiply external requests.
33. As an OVRCR user, I want refresh attempts bounded and backed off, so that repeated retries do not overload providers or bypass rate limits.
34. As an OVRCR user, I want credentials and provider response bodies excluded from diagnostics and snapshots, so that usage visibility does not expose account secrets.
35. As an OVRCR user, I want unsupported authentication or account modes explained, so that an absent subscription meter is not confused with a signed-out account.
36. As an OVRCR user, I want percentages and state text to work without color, so that accessibility and terminal themes do not change their meaning.
37. As an OVRCR user, I want existing Ready, Unread, Input requests, session metrics, and retained-session behavior preserved, so that quota reporting does not change unrelated session contracts.
38. As an OVRCR maintainer, I want real-path automated tests and native computer-use evidence, so that successful parser tests alone cannot certify the feature.

## Implementation Decisions

- **Required source-validation gates:** verify the documented quota fields on supported Claude versions; validate Codex's account-rate-limits RPC without creating a conversation, taking over a live client, or restarting an existing daemon for telemetry; validate a provider-permitted, read-only Grok native billing route. Record supported versions, authentication modes, window semantics, attribution, refresh side effects, and failure behavior. Public source inspection is permitted. Any private-account or paid/native-provider acceptance probe requires separate authorization and isolated resources. If a gate cannot be satisfied, report the exact blocker and stop dependent implementation. Do not silently reduce the three-provider scope.
- **Provider routes:** Claude quota comes only from the already-managed native status-line reporting path. Codex uses the documented account-rate-limits read/update protocol, not a copied ChatGPT HTTP endpoint. Grok uses typed native billing data if safely accessible; Superset's heuristic protobuf scanner is excluded. Direct internal HTTP or credential-reading alternatives require a separately approved design and provider permission.
- **Meaning:** this feature represents provider account/subscription allowance. Conversation/invocation tokens, estimated cost, context occupancy, API throughput headers, and organization invoices remain distinct. Do not derive account quota from session tokens or dollars. Ordinary bounded consumed percentages become remaining percentages by subtracting from 100. Nonfinite, negative, invalid, and over-limit values require explicit validation or state rather than misleading normal bars.
- **Windows:** retain source identifiers, durations or billing periods, consumed percentage, and reset timestamp. Display 5h and 7d only for matching verified windows. Missing windows remain unknown; genuinely different windows use their actual labels. Grok's reported weekly/monthly period is not evidence of an additional five-hour quota. Extra credit balances, model-specific allowances, and spend-limit types must not be silently folded into the ordinary general-window bars.
- **Source attribution:** maintain one selected source per provider, with nonsecret provenance. For native Claude observations, use the focused managed Claude session as the source when selecting among sessions; retain its last known observation with its source identity when focus moves elsewhere. Attribute it to the exact session, run, and Reporting generation, not an invented account identity. A newly selected Claude source replaces the old source rather than merging quotas. Codex/Grok use the validated native profile/account context. Conflicting or unverifiable identity cannot be presented as a combined current account quota. Reuse existing focus and identity mechanisms; do not add an account manager or parallel selection store.
- **Ownership:** the Server owns the bounded quota snapshot and any account collection schedule. The Reporter remains the owner of managed invocation reporting; provider receivers normalize native frames and do not duplicate lifecycle ownership. Runtime workers perform blocking external work outside the synchronous dispatcher, PTY parser, sole socket writer, and Dashboard draw path. Preserve one Server owner, one active Dashboard, and fifty-session support.
- **Shared protocol:** add provider-quota observations/snapshots separately from existing session token/cost types. Carry only validated window values, source identity, source generation, observation/check times, and sanitized availability state. Update protocol compatibility, constructors, exhaustive consumers, and public inspection/help behavior together. Do not repurpose Conversation or Invocation usage scope to mean account quota.
- **Collection limits:** account collection uses a conservative five-minute cadence while an active Dashboard exists, with one in-flight request per selected provider/profile. Native notifications may update values between scheduled reads. Manual refresh, if offered, uses the same in-flight/cooldown/backoff rules. Pause periodic external collection without an active Dashboard. Hiding the sidebar does not create a second collector. Claude remains event-driven through its managed invocation and has no OVRCR OAuth polling loop.
- **Failure isolation:** bound request duration, response size, queues, and retained state. Coalesce pending refreshes. Respect Retry-After where available and back off temporary/rate-limit failures. One provider's failure must not suppress another provider, disable activity reporting, or stall terminal input. Fence late responses by selected source generation and reject obsolete native session/run/binding observations.
- **Cache and freshness:** use an in-memory cache across Dashboard detach/reattach, not persisted quota history. A successful account read advances the last-check timestamp even if its value is unchanged. A native callback receipt is not proof of a new backend check; retain separate provenance. Mark native observations stale at the existing five-minute age boundary or after loss of their source authority. For periodically checked account snapshots, mark stale on fetch failure or a missed scheduled refresh, and always expose the last-check age. Future/unverifiable timestamps fail closed. A passed reset expires that window until authoritative replacement; never reset it locally to full allowance.
- **Presentation:** render the selected stacked remaining-allowance bars under a Quota left heading at the sidebar bottom, above the global footer. Keep provider labels and numeric percentages. Use existing terminal rendering primitives, not a chart dependency. Color may supplement the text but cannot carry meaning alone. Bar fill is approximate; the numeric percentage is authoritative. Missing data has no fabricated full/empty bar, and stale/over-limit states remain explicit.
- **Shared geometry:** reserve quota space through the same geometry used by rendering, tree scrolling, selection visibility, hover, mouse selection, close marks, and cursor placement. The reduced tree rectangle is authoritative. Do not draw quota over selectable session rows or alter pane subscriptions unnecessarily. At narrow widths, shorten/remove bars before clipping period labels, values, or state. At tiny heights, preserve a navigable tree and offer a compact details entry; when no safe space exists, hide the block while retaining menu/palette details access.
- **Interaction:** provide one quota-details action through the existing Browse menu/palette. Details include provider/source provenance, each actual window, remaining allowance, reset time, observation/check age, and sanitized availability reason. If block clicking opens details, it must share the same action and geometry and never fall through to session/PTY actions. Preserve overlay input priority and terminal-mode routing.
- **Persistence and security:** no durable quota database, raw response logging, credential collection, OAuth login UI, automatic reauthentication, or credential/profile modification. Do not persist prompts, transcripts, account emails, tokens, or provider response bodies for quota. Native auth handling and any unavoidable native refresh side effect must pass the source-validation gate. Update affected documentation, CLI help, and config examples with the eventual feature; do not install provider configuration during this specification task.

## Testing Decisions

- **Confirmed primary seam:** supply synthetic native-provider observations/responses through the production reporting/collector entry point, host an isolated real Server using the existing live-server fixture, consume its actual socket publications through the Dashboard, and assert the rendered quota block plus key/mouse navigation. Production construction, ownership, delivery, and redraw must be exercised; parser/helper mocks alone are insufficient.
- **Prior art:** reuse managed Claude status-line/reporting lifecycle integration coverage, the shared live-server fixture's private config/socket/workspace ownership, and existing Dashboard sidebar row-height, scrolling, input, and hit-testing tests. Extend the highest existing production seam instead of inventing a parallel telemetry test framework.
- **Focused contract tests:** test externally meaningful normalization and displayed states for consumed-to-remaining conversion; explicit 0/100 versus absent; over-limit, malformed and nonfinite values; independent windows; actual Codex durations/buckets; Grok weekly/monthly periods; and reset units/expiry. Do not assert internal helper structure or implementation-specific call ordering.
- **Ownership and attribution:** exercise fifty sessions sharing a source, multiple unrelated source contexts, focus-driven Claude source changes, Reporting generation changes, session reopen, delayed A-to-B-to-A responses, stale runs, and retired Dashboard connections. Assert that quota is neither summed nor applied to the wrong source, and that old connection cleanup cannot revoke a replacement owner.
- **Failure and refresh behavior:** exercise timeouts, blocked external work, malformed replies, unsupported auth, 401/403, 429/Retry-After, repeated manual refresh, and source disappearance. Assert bounded one-in-flight collection, retained last-good/stale data, independent provider failures, no secret-bearing diagnostics, and timely real PTY input/output while a collector is blocked. Use deterministic synchronization rather than timing guesses.
- **Freshness and persistence boundaries:** verify unchanged successful reads advance last-check provenance; replayed native samples do not falsely claim a backend check; reset expiry never manufactures full allowance; detach/reattach reuses the bounded cache without a duplicate worker; and Server restart does not resurrect quota from persistent storage.
- **Layout and interaction:** verify normal, narrow, short, hidden, split-pane, and empty-tree layouts; both 5h/7d rows where reported; last-row visibility and selection; tree scroll limits; quota exclusion from session close/selection hit-tests; menu/palette details; and preservation of terminal input and overlay priority. Treat literal labels, glyph widths, color-independent text, and accessible state descriptions as behavior.
- **Native CUA:** run the actual app from the reviewed checkout with disposable resources. Verify visible bars/percentages, waiting/stale/error states, resizing, sidebar hide/show, keyboard details access, mouse behavior, and real terminal input. Retain screenshots and accessibility evidence. Headless rendering cannot substitute for this acceptance.
- **Provider acceptance and regression:** supported provider versions/auth modes require their own explicitly authorized, isolated native evidence. Keep this distinct from synthetic tests and CUA. Run required affected and workspace regression/lint checks on the eventual implementation revision, confirm filters execute tests, and report failed/skipped/unavailable checks as gaps. No live provider calls or application tests were run to publish this spec.

## Out of Scope

- Implementing the feature during this specification/publication task.
- A Claude-only release or permanent Grok placeholder presented as three-provider support.
- Arbitrary provider/harness support beyond Claude, Codex, and Grok.
- A provider login/account manager, automatic account discovery through credential stores, account switching, profile provisioning/removal, or token refresh implemented by OVRCR.
- Direct Claude OAuth credential forwarding, Superset's Grok protobuf heuristic, or other internal-endpoint fallbacks without a separately approved design and provider permission.
- Historical token/spend charts, invoice reconciliation, context-window bars, extra-credit purchasing/redemption, leaderboards, analytics publication, and quota-exhaustion prediction.
- A new Server, Bridge-owned quota collection, Dashboard-owned network polling, duplicated socket writers, a new agent SDK, Tokio, a chart library, or a persistent quota store without an independently established requirement.
- Paid/model work merely to refresh usage, broad private-account inspection, changes to shared provider configuration, live-session disruption, commits, pushes, PRs, or merges without separate authorization.

## Further Notes

The user selected remaining-allowance bars with separate reported 5h and 7d rows, requires Claude/Codex/Grok, accepts native Claude reports only, and confirmed the live Server/socket/Dashboard test seam. This issue specifies the desired feature and a safe stop-on-blocker execution contract; it does not claim all native collection interfaces have already passed acceptance.

Research inspected OVRCR revision `14c7fe5ffff7e0dd90a920f2006f35c4b3a97c25`, [Superset revision `149e20ef52ffda02859cc0eeba60cb3f8fb01889`](https://github.com/superset-sh/superset/tree/149e20ef52ffda02859cc0eeba60cb3f8fb01889), [Codex revision `804d6306e84f570393cdd1eec94c41464f503b1a`](https://github.com/openai/codex/tree/804d6306e84f570393cdd1eec94c41464f503b1a), and [Grok Build revision `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8`](https://github.com/xai-org/grok-build/tree/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8).

Superset's Usage page combines account quota with separate token/cost history. Its quota readers directly use native OAuth credentials, share a five-minute host cache, and display used percentages. Its Grok reader heuristically parses a private RPC and exposes only an inferred Weekly window. These are source observations, not provider permission, a stable schema, or proof that OVRCR can safely reproduce the integration.

Primary provider references are [Claude status-line quota fields and update behavior](https://code.claude.com/docs/en/statusline), [Anthropic credential-use restrictions](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use), [Codex app-server account endpoints](https://developers.openai.com/codex/app-server/), and [Grok CLI usage/context commands](https://docs.x.ai/build/modes-and-commands). Organization API usage, spend, and throughput APIs are not interchangeable with subscription-window allowance.

The principal unverified items are supported-version Claude quota fields, precise Claude source attribution, Codex read-only coexistence/auth-refresh effects, and a safe Grok typed native billing access route. Resolve them through the required gates. If a provider-permitted native route is unavailable, report the blocker rather than accessing credentials, inventing quota, or weakening the acceptance criteria.
