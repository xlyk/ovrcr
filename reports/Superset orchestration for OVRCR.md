# Superset orchestration for OVRCR

At the 2026-11-02 America/Los_Angeles source snapshot, Superset’s `orchestrate` skill is a coordinator procedure over workspaces and terminal-agent sessions; its documented launch path does not persist a parent-child workflow graph. ([Pinned orchestration guide](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/apps/docs/content/docs/orchestration.mdx#L6-L36), [agent run input](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/trpc/router/agents/agents.ts#L138-L168)) Its strongest reusable ideas are explicit task ownership, isolated parallel work, bounded worker instructions, evidence checks, and human-controlled integration. OVRCR already implements those ideas through a durable, Server-owned assignment workflow. The only candidate addition identified in the source comparison is to make ready-set-before-wait dispatch explicit in the existing delegation procedure; the plan includes a no-change gate if the current wording already guarantees it. ## The orchestrate skill makes the agent its coordinator

`orchestrate` triggers on fan-out, splitting tasks across agents/workspaces/hosts, handoffs, and worker monitoring. It excludes ordinary single-agent workspace management and automation. Its essential behavior is a prompt-led protocol over existing commands: the skill tells the active model how to keep the plan, while the product creates workspaces and sessions and exposes status/input. ([Plugin orchestrate trigger and tool restrictions](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L1-L8), [standalone orchestration guide](https://github.com/ParadevAI/skills/blob/a56e0162c5631d9859e70872323bf986f4a926c6/skills/superset-orchestrate/SKILL.md#L2-L24))

The coordinator first checks authorization, CLI schema or help, and the availability of terminal operations. It explicitly resolves local versus remote host and workspace, verifies a remote host is online, and selects an agent that creates a controllable terminal session. A `--agent superset` chat session cannot be managed with terminal controls, so it is not interchangeable with a terminal worker. Adding an SSH host modifies another machine and the guide requires user approval plus prerequisite checks. The coordinator keeps a task table with a stable task ID, dependencies, workspace, host, terminal/session ID, status, and result. Tasks should have shallow dependencies; independent editors get separate branches/workspaces; shared workspaces are limited to read-only or intentionally disjoint edits. ([Plugin preflight and routing](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L14-L45), [task table and worker prompt](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L29-L76))

Each worker prompt states its objective, allowed workspace/files, acceptance criteria and checks, dependency findings, scope limits, and required handoff. The coordinator dispatches every currently ready independent task, then records the result’s `sessionId` as the terminal ID and verifies that a launch result says `kind == terminal`. Workers are asked to end with `SUPERSET_WORKER_DONE` or `SUPERSET_WORKER_BLOCKED` plus a concise summary, files, checks, and handoff. Those markers are a prompt convention. The coordinator must still inspect the surrounding output and evidence; the text does not become a durable workflow event merely because it has a sentinel string. ([Plugin worker prompt and launch procedure](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L47-L96), [completion and verification procedure](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L160-L181))

Monitoring combines `agents wait`, `terminals read`, and `terminals send`. When the coordinator loses context, it can relist terminals but still needs its own task-to-terminal map because terminal inventory does not restore semantic task ownership. It reads output before answering permission prompts, may use explicit keys to continue or escape, and checks the screen after waiting. For completion it verifies the matching worker report and evidence, passes accepted dependency findings to downstream tasks, and re-dispatches failures only after changing the prompt, inputs, or worker. Branches do not merge automatically. Risky or overlapping changes get independent review. Finished terminals remain available for inspection; workspace deletion is separately scoped. A summary page is offered only with agreement and has organization visibility by default. ([Plugin monitor and message procedure](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L97-L159), [handoff, publish, and cleanup](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L181-L204))

The documented path is therefore a parent agent, CLI, host service, workspace/PTY worker, and lifecycle hooks. The parent’s task breakdown, dependencies, and integration decision live in its context; the cited launch inputs do not contain a parent workflow ID. The diagram is a synthesis of the pinned CLI and host-service implementation, not a server-owned orchestration state machine. ([Agent run input](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/trpc/router/agents/agents.ts#L138-L168), [workspace dispatch](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/trpc/router/workspace-creation/shared/dispatch-agents.ts#L5-L52))

A worker launch is an agent process in a workspace, normally a separate local Git worktree/branch or cloud clone. The CLI and MCP can create a workspace with agent launches or add an agent to an existing workspace. The host dispatches multiple requested launches concurrently and returns a per-agent `ok`/`error` result and session ID; a successful command envelope is not enough if one of those launch entries failed. A local worktree isolates a checkout and branch, not machine processes, network access, or files outside the worktree. The launch input includes workspace, agent, prompt, and optional provider settings/session operations but no parent agent or child workflow ID. ([CLI create and launch result](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/apps/docs/content/docs/cli/getting-started.mdx#L150-L205), [concurrent workspace dispatch](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/trpc/router/workspace-creation/shared/dispatch-agents.ts#L5-L52), [host launch input](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/trpc/router/agents/agents.ts#L138-L168), [worktree isolation limits](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/apps/docs/content/docs/faq.mdx#L50-L60))

**`agents wait` observes lifecycle and process state; it does not evaluate task success.** Status derives from Paradev-installed lifecycle hooks and terminal liveness, and works only for sessions launched through that path. The pure wait helper’s `idle` predicate includes an exited process, but the CLI command separately reports an observed terminal exit as an error; `settled` can also cover interruption and permission blocking. A `Stop` event means the turn ended, not that its goal passed. A `Failed` event has a separate visual mapping but is mapped to `idle` by the cited run-state helper. After input, the CLI also expects a new hook event within its stall window. These labels are observability signals; task completion still requires inspecting output and verifying the work. ([Status documentation](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/apps/docs/content/docs/agent-status.mdx#L17-L27), [wait state and exit handling](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/cli/src/lib/agent-wait.ts#L21-L75), [wait command](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/cli/src/commands/agents/wait/command.ts#L44-L71), [state mapping](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/shared/src/agent-status.ts#L22-L53))

**`terminals send` is PTY input, not durable messaging.** With a live agent binding, the host writes a bracketed paste and Enter into the terminal; with no binding, it writes terminal input. The interface has no durable mailbox or message receipt. If the caller loses a reply, it cannot infer whether a follow-up reached the model and should inspect before retrying. `terminals read` returns screen plus recent scrollback; `agents read` attempts to fetch a provider transcript. Host `snapshot` composes projects/workspaces, terminals, hook-derived states, and desktop pane layout, but is not a source of task success and does not read workspace files or pixels. Public MCP exposes terminal read/send but no `agents.wait` tool; clients must use CLI wait or compose read polling themselves. ([Terminal send implementation](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/trpc/router/terminal/terminal.ts#L162-L208), [PTY send behavior](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/terminal/terminal.ts#L1187-L1309), [MCP tool surface](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/apps/docs/content/docs/mcp-server.mdx#L14-L26))

Three concepts that can all look like “delegation” must stay separate. First, the skill-coordinated worker is a separate terminal agent launched into a workspace and tracked by the coordinator’s task map. Second, Claude/Codex native subagents are child agents started inside one provider session; Paradev records their hook-derived roster in host memory, with provider-specific parsing for Claude and Codex and generic fallback elsewhere. That in-memory roster is capped at 64 entries per terminal and child entries expire after ten minutes without activity; it is not a durable work graph or a worker concurrency limit. Third, scheduled automation dispatches a configured prompt from a schedule/event, with handoff states such as workspace-created, missed, and failed; it is not a child-worker scheduler. Webhook triggers have no de-duplication, and “created” means a workspace handoff, not successful work. ([Native child roster](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/terminal-agents/types.ts#L26-L49), [roster expiry and cap](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/terminal-agents/store.ts#L73-L90), [provider hook parsers](https://github.com/ParadevAI/Paradev/tree/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/terminal-agents/subagent-harnesses), [automation state and triggers](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/apps/docs/content/docs/automations.mdx#L70-L119))

Recovery is asymmetrical. The host persists provider session identifiers and some binding state and can resume supported agents after terminal failure, but the coordinator’s plan, worker-to-task mapping, report, and acceptance decision have no matching durable workflow record in this orchestration path. A normal branch-based workspace create retry may reuse the workspace and relaunch its agent; workspace reuse is not launch idempotency. Superset has a lower-level same-request ID path, but the cited public CLI/MCP create interfaces do not expose it. Context handoff is also bounded: it seeds from recent terminal context and caps at 36,000 characters by default, despite broader “full context” wording. ([Persistent binding and resume](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/terminal-agents/persistence.ts#L25-L65), [workspace reuse and launch behavior](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/trpc/router/workspaces/workspaces.ts#L1136-L1144), [agent relaunch path](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/packages/host-service/src/trpc/router/workspaces/workspaces.ts#L1301-L1384), [handoff context cap](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/apps/docs/content/docs/cli/cli-reference.mdx#L1327-L1335))

MCP is an alternate organization control surface, not a prerequisite for the skill-driven workflow. It can create workspaces and agents and read/send terminal input; OAuth is used for interactive authorization, while the docs describe API keys as granting full organization access. The standalone `superset-mcp` setup guide is specifically about configuring a client for that product MCP service. Plugin `integrations`/`plugins` instead manage and invoke third-party tools through Paradev’s proxy. Treating these as interchangeable would conflate separate trust and control boundaries. ([MCP authentication](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/apps/docs/content/docs/mcp-server.mdx#L240-L288), [standalone MCP guide](https://github.com/ParadevAI/skills/blob/a56e0162c5631d9859e70872323bf986f4a926c6/skills/superset-mcp/SKILL.md#L2-L60), [plugin integration flow](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/integrations/SKILL.md#L20-L86))

## OVRCR already owns the harder coordination state

The Server binds parent identity and controller epochs; workflow recovery reconciles authority without launching or resending a child. This is a stronger state foundation than Superset’s ephemeral coordinator map. The correct mapping is already present in OVRCR’s operation contract: **observe, then collect**, without treating `ovrcr_wait` as equivalent to Superset CLI `agents wait`. OVRCR’s wait is a content-free observation capped at 20 seconds; cancelling it leaves child work running. The parent explicitly collects the exact current child submission, then accepts according to the task’s evidence contract. OVRCR’s authenticated handles and receipts, control epochs, and lost-reply reconciliation already replace Superset’s text-marker and PTY-send conventions. The small candidate change is to write each ready assignment into the existing workflow record and start all currently ready independent assignments before the first wait; then observe/collect each exact result. Any dependency should use `ovrcr_dependencies` only when it represents a real accepted predecessor. Parallel starts remain within shared capacity and actual provider/model availability. ## Conclusion

Superset’s coordinator procedure is a useful reference for dispatch order, while its worker lifecycle remains session-oriented and its task map stays in model context. OVRCR already has a durable workflow and identity model, so the first proposal is intentionally narrow: confirm that the direct delegation reference records the ready set before waiting, and add that sequence only if missing. Broader parent authority, provider reach, external publishing, or persistent state each need a new explicit design decision.
