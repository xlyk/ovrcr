# OVRCR capability audit and proposed Superset-style skill plan

Audit basis: local `main` at `bdd30e77d0c2fab589ff2c605bcf5f0e31cd1944`; working tree was clean and the local upstream ref was 0/0 at inspection. No live remote query was made. This is a read-only audit; no tests, app/provider runs, issues, pull requests, or product changes were made. Recommendations below are proposed and unapproved.

## 1. Which OVRCR primitives already cover multi-agent coordination?

### Takeaway

OVRCR already has a durable, Server-owned assignment and workflow system behind its managed Pi extension. It covers bounded parallel child assignments, attribution, waiting and collection, questions, control transfer, dependency evidence, acceptance, delivery, and retention. The matching plan should translate Superset orchestration instructions onto these primitives instead of rebuilding worker launch, a task table, a monitor loop, or a scheduler.

### Cited Findings

### Inferences

- For the core orchestration path, OVRCR needs skill instructions adapted to its durable IDs and receipts, not a new assignment store or marker protocol. A result should come from `ovrcr_collect` and be accepted separately, not inferred from terminal title, activity, Ready, or a worker-authored completion line.
- Superset's explicit host/workspace preflight maps to OVRCR's `ovrcr_capabilities` and Server-resolved project/workspace IDs. Its parallel fan-out maps to multiple bounded `ovrcr_start` calls within OVRCR's shared capacity. Its short polling maps to `ovrcr_wait` plus collect, without polling every child or using terminal text as the state owner.
- Superset's prompt envelope should not be copied as OVRCR's success protocol. OVRCR uses authenticated immutable publication and exact acceptance evidence; the skill can still require readable progress/failure reports, but the report itself does not replace the Server receipt.

### Gaps

- Child capacity is shared with all OVRCR live sessions, not an independent orchestration pool. Default policy allows Pi only and up to 50 live children, further constrained by the 50-session Server ceiling and configured free-slot reserve. Capacity is advisory until serialized Server admission. [Delegation policy](</Users/xlyk/Code/ovrcr/crates/ovrcr-runtime/src/server/delegation_policy.rs:8>), [fifty-slot invariant](</Users/xlyk/Code/ovrcr/docs/development/architecture.md:95>), [default provider policy](</Users/xlyk/Code/ovrcr/crates/ovrcr-protocol/src/settings.rs:1628>).
- Native child-provider coverage is tiered: Pi can do bounded coding; Codex and Claude are read-only research routes with explicit native/backend requirements; Grok appears in the harness enum but current capability discovery refuses unsupported harnesses. The tool must report the actual available choice and never substitute. [Contract validation](</Users/xlyk/Code/ovrcr/crates/ovrcr-protocol/src/delegation.rs:158>), [capability discovery](</Users/xlyk/Code/ovrcr/crates/ovrcr-runtime/src/server/delegation.rs:800>), [policy resolution](</Users/xlyk/Code/ovrcr/crates/ovrcr-runtime/src/server/delegation_policy.rs:8>).
- OVRCR rejects mandatory `max_cost_microusd`, `max_output_tokens`, and `max_native_children` bounds; it does not claim descendant-cost accounting. If Superset skills depend on such limits, that is a real product-contract gap and needs a separate design, not an unenforced skill promise. [Delegation limits](</Users/xlyk/Code/ovrcr/crates/ovrcr-protocol/src/delegation.rs:25>).

## 2. Which Superset-style support skills map to existing OVRCR surfaces, and where are the real gaps?

### Takeaway

Setup and scheduled automation already have OVRCR CLI/docs, and provider doctor commands exist. Standup can be a read-only CLI skill if a composed, non-atomic digest is acceptable. Clear gaps are a general parent-facing MCP endpoint/non-Pi orchestration entry point and a single host snapshot that includes pane layout. A separate, conditional gap is observability/budgeting of arbitrary subagents created inside a provider process; it is outside the current OVRCR child-assignment contract and unsupported by required native-child limits.

### Inferences

- Current OVRCR already has equivalent concepts for project/workspace setup, scheduled tasks, provider diagnostics, and parent-controlled child sessions. These support skills can mostly be authorship/discoverability work, not new Rust runtime services.
- The `mcp` support skill cannot simply be copied as a prompt if its job is to configure a generic host to call OVRCR parent operations. OVRCR currently has an explicit Pi tool transport and a narrower child publication transport. If cross-host control is required, design an adapter to the existing authenticated Server protocol and retain the Pi implementation as a compatibility caller.
- The Superset-native-subagent roster is not required to reproduce the reviewed `superset-orchestrate` prompt workflow. Treat it as a separate optional capability; do not add a second subagent registry unless the user explicitly needs that behavior and accepts a design for ownership, persistence, limits, and provider coverage.

### Gaps

- There is no global system health/doctor contract or standalone OVRCR standup skill in the inspected checkout; provider-specific doctor and CLI inventory are present. Confidence is high for the skill/package file inventory, medium for absence of a hidden host-level feature because the audit was source-scoped, not a full product search.
- There is no general parent MCP service in the inspected OVRCR entry point. Confirm whether MCP is a required host surface before product design; no implementation or server endpoint is proposed as approved.
- Superset's current provider-native child roster is not durable workflow state and is not a prerequisite for the skill-driven worker fan-out. Whether to replicate it is unresolved and should stay out of the first slice.

## 3. What is the smallest reuse-focused replication plan?

### Takeaway

Recommended first phase: keep OVRCR's existing Server contract, adapt the skill layer, and add only support skill files whose jobs can be expressed through current documented CLI/API calls. Make generic MCP access and native-subagent accounting explicit future decisions. Do not add an async runtime, a second database, a duplicate scheduler, a worker DAG engine, or a second Dashboard/Server owner.

### Cited Findings

- The architecture guide requires one owner per state domain, keeps the Server synchronous, and warns against adding Tokio/agent dependencies or crates without an approved concrete design. The runtime guide requires one production spawn path, bounded state/queues, and the existing lock/publication boundary. [Architecture constraints](</Users/xlyk/Code/ovrcr/docs/development/architecture.md:15>), [runtime ownership constraints](</Users/xlyk/Code/ovrcr/docs/development/runtime.md:13>).
- Existing files already divide skill procedures from product contracts: package entry/discovery (`package.json`, `pi/extension.ts`), shared Pi tools (`src/ovrcr-pi-runtime.ts`), skill dispatcher/references (`pi/skills/ovrcr-orchestrator/`), CLI operation skill (`.agents/skills/ovrcr/`), public assignment contract (`docs/pi-research-assignments.md`), scheduled task guide (`docs/scheduled-tasks.md`), and Server implementation (`crates/ovrcr-runtime/src/server/delegation_*.rs`).
- Existing acceptance covers package discovery/one-owner behavior, the public managed-Pi child lifecycle, control/recovery, coding workspace, dependencies, and independent review. For future changed tool behavior, use those owning tests as starting points; run none for this research-only plan. [Package test](</Users/xlyk/Code/ovrcr/tests/pi_package.rs:101>), [public delegation test](</Users/xlyk/Code/ovrcr/tests/pi_delegation.rs:122>), [task schedule admission test](</Users/xlyk/Code/ovrcr/tests/task_schedule.rs:205>).

### Inferences

**Proposed phases and file map (unapproved):**

1. **Procedure reuse, no product changes.** Keep `ovrcr-orchestrator` as the single core orchestrator skill. Compare the richer marketplace procedure's host preflight, dispatch, monitor, prompt, publishing, and cleanup gates against existing `delegation.md`, `workflow.md`, `implementation.md`, and `records.md`; import only behavior that fits OVRCR's local Server/authorization contract. Replace worker marker checks with `ovrcr_inspect`/`ovrcr_wait`/`ovrcr_collect`; map explicit project/workspace IDs to `ovrcr_capabilities`/`ovrcr_start`; preserve question, human-control, acceptance, delivery, and archive boundaries. Do not add host provisioning, page publishing, pane automation, or notification promises without a separate scope decision.
2. **Optional support skills, still docs-only.** Reuse `.agents/skills/ovrcr` and existing install/task/doctor guides. If independent skill triggers are wanted, add small setup/standup/doctor/automate/10x instructions under the chosen target skill root; wire Pi-distributed directories through `package.json` only when Pi package discovery is required. Candidate standup/doctor/automate procedures should call existing `--json` CLI, events, provider doctor, or task commands and state what they cannot prove. Avoid copying entire user guides into multiple skill roots; link canonical docs. Keep feedback/contribute out of the multi-agent slice.
3. **Conditional non-Pi MCP adapter.** Only if the user requires Codex/Claude/another MCP host as an orchestration parent, specify parent identity authentication, tool schemas, request idempotency, lost-reply recovery, and compatibility against `src/ovrcr-pi-runtime.ts`. Add a thin protocol adapter that calls the existing Server requests/receipts; no new task persistence or state owner. This requires a later design decision and product work.
4. **Conditional host snapshot/publish/UI parity.** If the selected scope requires a race-consistent host-wide snapshot including panes, remote host provisioning, organization-visible page publishing, parent pane/attach automation, or workflow-level notifications, define the exact read/write/authorization contract first. A read-only standup skill may compose current OVRCR JSON reads if inter-read drift and missing pane geometry are acceptable; otherwise add one bounded Server read over existing owners, not a new store. Existing project/workspace creation, coding candidate capture, Dashboard panes, and provider Ready notifications are not exact substitutes. These features are outside the minimum multi-agent skill replication.
5. **Conditional provider-native child accounting.** Only if the scope includes nested native subagents, first define which providers expose trustworthy child lifecycle and cost evidence. Do not treat native process count as descendant-work proof. Add limits/roster only after deciding persistence, bound sizes, restart/recovery, and failure states; the current Server correctly rejects an unsupported mandatory `max_native_children` limit.

**Acceptance and failure cases for a future implementation:**

- Package test proves the local skill is discovered by the intended host and both injected/package Pi entries retain one Reporter/workflow authority. Do not infer feature availability from package selection metadata alone.
