## 2. Direct orchestration skill and coordinator protocol

### Takeaway

`orchestrate` is the sole direct multi-agent coordinator skill in the product plugin. It teaches the current agent to plan and supervise workers using workspaces and terminal sessions. The CLI provides isolation and session transport; the coordinator itself retains the task map, dependencies, status, verification, and integration decisions in its working context.

### Cited Findings

- The plugin skill triggers on delegation, parallelization, fan-out, splitting across agents/workspaces/hosts, handoffs, or worker monitoring; it excludes ordinary single-agent workspace/task/automation management. Its Claude plugin frontmatter limits shell calls to `superset`/`paradev` commands. [Plugin skill lines 1–8](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L1-L8)
- **Preflight and routing:** it checks auth and discovers whether terminal `list`, `read`, `send`, and `close` commands exist, using `superset schema` with a help fallback; it asks for an update if commands are missing and skips unavailable newer features. It resolves host, workspace, and terminal-capable agent before dispatch. It requires explicit local/workspace/host routing, confirms a remote host is online, and warns that `--agent superset` creates a chat session that terminal controls cannot manage. Adding an SSH host changes that machine, so it requires user go-ahead and enumerates prerequisites. [Plugin skill lines 14–27](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L14-L27)
- **Plan and worker input:** it asks the coordinator to keep a table with stable task ID, dependencies, workspace, host, terminal/session ID, status, and result. Statuses are `pending`, `ready`, `running`, `completed`, `blocked`, or `failed`. Tasks should be independent with shallow dependencies; parallel editors get separate workspaces/branches, while shared workspaces are for read-only or explicitly disjoint work. Organization tasks are issue-tracker records, not a DAG. Each bounded worker prompt carries objective, allowed workspace/files, acceptance and verification, dependencies/findings, scope protection, and the completion format. [Plugin skill lines 29–76](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L29-L76)
- **Dispatch and outputs:** create an isolated workspace when needed, then call `superset agents create` with `--workspace`, optional `--host`, `--agent`, `--effort`, `--attachment`, `--prompt`, and `--json`. The documented result is `{kind, sessionId, label}`; require `kind == terminal` and save `sessionId` as the terminal ID. Launch every currently ready independent task before monitoring. The worker is asked to end with `SUPERSET_WORKER_DONE` (summary, files, checks, handoff) or `SUPERSET_WORKER_BLOCKED` (reason and need). [Plugin skill lines 47–96](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L47-L96)
- **Monitoring and messages:** recover terminal IDs with `terminals list` after losing context, but keep the task-to-terminal mapping because listing does not identify semantic ownership or completion. `terminals read` returns screen text (`text` in JSON) for checking the envelope and surrounding evidence; `terminals send --text` supplies follow-up or dependency results. For a permission prompt/interrupt, the skill documents `--keys enter`/`esc` and says to read first. `agents wait --until settled` returns `idle` or `blocked`; keep waits short and read the screen afterward. If unavailable, use measured short `terminals read` polls. `terminals wait --match` is for screen conditions, not agent state. `snapshot --host` and pane commands offer fleet/UI views. [Plugin skill lines 97–159](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L97-L159)
- **Completion, handoff, and cleanup:** advance a task only after reading the matching worker envelope and checking evidence; send dependencies to downstream workers; re-dispatch failures only after changing inputs/prompt/worker; independently verify risky or overlapping work. Summaries distinguish workspace/branch, files, checks, blockers, and integration order, and worker claims from coordinator checks. Branches do not merge automatically. A notification is optional. A multi-workspace page is offered and published only after agreement; its content quotes worker output and is organization-visible by default. Keep finished terminals for inspection; close only when requested or clearly part of the workflow. Deleting a workspace is a separate destructive action requiring explicit scope. [Plugin skill lines 160–204](https://github.com/ParadevAI/Paradev/blob/4cb2bf762b462001b2e535c9955624cd9c2bf0ed/plugins/superset/skills/orchestrate/SKILL.md#L160-L204)
- The portable external skill uses the same core pattern (preflight, dependency table, isolated workspaces, bounded prompt, text envelopes, read/send monitoring, verification, no automatic merge) but is 158 lines and does not include the product plugin's schema/version handling, `agents wait`, snapshots, panes, pages, or notifications. It checks `terminals --help` directly and does not declare a Claude-specific `allowed-tools` list. [Standalone `superset-orchestrate` lines 2–6, 10–24, 26–74, 75–132, 133–158](https://github.com/ParadevAI/skills/blob/a56e0162c5631d9859e70872323bf986f4a926c6/skills/superset-orchestrate/SKILL.md#L2-L158)
- The current product docs describe the same one-coordinator flow: separate workspaces, `agents create`, `terminals read`/`send`, then verify structured worker completion before integrating. [Agent Orchestration docs lines 79–105](https://docs.paradev.com/orchestration)

### Inferences

- The reusable design pattern is explicit ownership of task-to-session mapping, dependency-aware fan-out, bounded worker contracts, evidence checks, and human-controlled integration. Superset's distinguishing coordinator state is ephemeral: it lives in the coordinator's context, rather than in a persisted orchestration DAG.
- The worker envelope is a prompt convention, not a durable event or runtime-enforced completion record. The skill explicitly says malformed/missing envelopes require inspecting the full snapshot, and task completion requires checking evidence. A replica should treat the text as worker-reported data, not proof.
- To adapt the pattern to OVRCR, preserve the separation between worker session transport and the coordinator's durable orchestration state. Prefer OVRCR's structured receipts/state transitions over parsing Superset's text marker convention; the marker protocol is a portable fallback, not a strong runtime guarantee.

### Gaps

- The skill specifies example CLI contracts, but it is not the CLI/API schema. Exact flags, availability, state fields, and behavior are version-dependent; the prompt itself tells agents to inspect `superset schema`/help and fall back when features are absent.
- The skill does not prescribe an automatic merge algorithm, durable dependency graph, concurrency limit, or numeric polling interval. The coordinator is expected to choose/track those within the task context.

### Inferences

- For an OVRCR plan, the direct port is the coordinator behavior: explicit task ownership, dependency-gated dispatch, worker scope/acceptance contracts, session-to-task mapping, structured completion/block signals, independent review, and human-controlled integration. The project-prep, monitor, and host-health skills are optional support workflows; panes/pages are presentation surfaces, not core orchestration.
- The high-value product distinction is that Superset combines isolated worktrees and terminal transport with a coordinator protocol. The protocol remains prompt-driven; a replica can keep the useful workflow while grounding state transitions in OVRCR's durable receipts instead of adopting marker parsing or transient coordinator context.

### Gaps

- Exact MCP tool parameters are dynamic; the skill itself directs agents to request the live `tools/list` schema. Its pinned claim of “27 tools” is not a stable contract, and current docs describe additional Pages/Organization capabilities, so use current schemas if that surface matters.
- The product plugin contains browser/computer/page/panes/environment/integration helpers beyond the portable nine-skill bundle. Which set is present in a specific release or agent client depends on its delivery path; the current docs and pinned repository lists are not identical.
