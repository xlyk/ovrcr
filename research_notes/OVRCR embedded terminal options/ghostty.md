# Ghostty and libghostty as OVRCR's embedded terminal

Audit context: OVRCR was read at `main` HEAD `56ef7694318b5a1ec0514424b503dd2d004ff6a1`; no files were changed. Upstream Ghostty `main` was `46f1cea1a10a19bef97a8a0f5948e660d0b74fe2` (commit time 2026-11-13 17:13:48 UTC; `build.zig.zon` says `1.4.1-dev`, Zig 0.17.0). The separately tagged `libghostty-vt` `vt-1.0.1` points at `108cacb17ed8990840cd14abfce43d8ed8503ca1`; its annotated tag time is 2026-11-11 20:10:46 UTC. The inspected cmux `main` was `b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75` (2026-11-13 14:51:52 UTC), pinning `manaflow-ai/ghostty` commit `ef4f1570d62117ebc51e3b0f07ad4f34032267b6` (2026-10-18). [Ghostty main commit](https://github.com/ghostty-org/ghostty/commit/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2), [build metadata](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/build.zig.zon), [vt tag object](https://api.github.com/repos/ghostty-org/ghostty/git/tags/e9dc690b08bde7e2ec9c7aff8a18a85c9cade46d), [cmux main commit](https://github.com/manaflow-ai/cmux/commit/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75), [cmux Ghostty fork commit](https://github.com/manaflow-ai/ghostty/commit/ef4f1570d62117ebc51e3b0f07ad4f34032267b6).

The assessment assumes the confirmed product contract: a Swift macOS app hosts the bundled Rust Dashboard as a child in a terminal surface, while the independent Rust server remains the owner of live sessions and capacity. The terminal engine is not expected to own those long-lived sessions.

## What is the current API and distribution status of full libghostty versus libghostty-vt?

### Takeaway

The full Ghostty terminal surface is technically embeddable, but the current upstream header explicitly calls it `libghostty-internal`, says the macOS app is its only consumer, and says it is not designed for external use. The documented third-party library is a different product, `libghostty-vt`: it has a released, Swift-usable XCFramework and C ABI stability from 1.0, but provides terminal state/render data rather than a complete rendered AppKit view.

### Cited Findings

- The current full-engine header starts by warning that `include/ghostty.h` is an internal embedder API, tailored to the macOS app; external embedders are directed to `libghostty-vt` and related libraries instead. The header says most functions are undocumented and some are macOS-specific. [Current `ghostty.h` header](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/include/ghostty.h#L1-L10)
- A maintainer said the old goal of making the full embedded API work for general use had been superseded by `libghostty-vt` for pure terminal emulation; another maintainer answer says the full header is now called `libghostty-internal`, is primarily designed for the macOS app, and external users should maintain their own fork if they need it. [Discussion #11722](https://github.com/ghostty-org/ghostty/discussions/11722), [Discussion #14360](https://github.com/ghostty-org/ghostty/discussions/14360)
- The root README still describes `libghostty` as an embeddable library. The more specific current header and maintainer answers narrow that wording: a C API exists, but the full surface API does not have an external-consumer support contract. Ghostty's 1.4 release notes also say full `libghostty` is not directly part of that Ghostty app release, while discussing the separate VT library. [README](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/README.md#L125-L143), [1.4 release notes](https://ghostty.org/docs/install/release-notes/1-4-0)
- The source tag `vt-1.0.1` has a header that states the C ABI is stable from 1.0. Its tag points to commit `108cacb17ed8990840cd14abfce43d8ed8503ca1`; the tag metadata dates it to 2026-11-11. [Tagged `vt.h`](https://github.com/ghostty-org/ghostty/blob/vt-1.0.1/include/ghostty/vt.h#L1-L13), [tag metadata](https://api.github.com/repos/ghostty-org/ghostty/git/tags/e9dc690b08bde7e2ec9c7aff8a18a85c9cade46d)
- `libghostty-vt` publishes a Swift-compatible XCFramework with static libraries for macOS arm64 and x86_64, iOS and the iOS simulator, plus headers and a module map. SwiftPM can use it as a binary target with a checksum. The release files include source, docs and checksums; the docs prescribe Zig 0.17 for builds. [Install and release files](https://lib.ghostty.org/vt/installing.html), [packaging guide](https://github.com/ghostty-org/ghostty/blob/vt-1.0.1/PACKAGING-LIBGHOSTTY.md#L88-L101)
- In upstream Ghostty `main` at the audit revision, `build.zig.zon` identifies the source as `1.4.1-dev` and requires Zig `0.17.0`. This is current-main metadata, not a claim that a full-engine third-party SDK is released. [Build metadata](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/build.zig.zon#L1-L10)
- The VT API's `GhosttyTerminal` keeps screen, scrollback, cursor, styles and modes, but the docs say it does not draw and does not talk to a PTY. `GhosttyRenderState` provides the cell/cursor/color snapshot for a consumer's renderer. [Terminal API](https://lib.ghostty.org/vt/group__terminal.html), [render-state API](https://lib.ghostty.org/vt/group__render.html)

### Inferences

- For OVRCR, the upstream-supported path is `libghostty-vt` plus an OVRCR-owned AppKit/Metal renderer and input host. Using the full Ghostty surface means pinning and maintaining the internal API as a fork or tolerated downstream integration, rather than adding a stable upstream package dependency. This follows from the tagged VT release path and the full header's own external-use warning.
- The separate VT library is the lower-risk choice for ABI churn and binary acquisition, but it shifts substantial rendering and host work to OVRCR. That is a weaker fit if the intent is to preserve almost all current workspace UI and avoid building terminal presentation behavior again.

### Gaps

- I did not find an upstream full-engine binary target, Swift package, external API stability promise, or supported deployment-target/architecture matrix. The full API's minimum macOS version is therefore unknown; do not transfer Ghostty.app's minimum OS to this internal library without checking the built artifact.
- The VT API has a stable C ABI from 1.0, but the current accepted-version policy for future 1.x API additions and any Swift source-level wrapper stability were not separately established.

## Does the engine fit OVRCR's process, keyboard, terminal-protocol and native-input contract?

### Takeaway

The full C surface exposes the mechanisms needed to start a command in its own terminal surface and feed it keys, text, paste, preedit, mouse and focus events. That fits the planned outer child process (`ovrcr` Dashboard) while OVRCR's independent Rust server continues to own inner session PTYs. The full API is still only an engine surface: the Swift app must own AppKit event mapping, host callbacks, accessibility and product-specific key routing.

### Cited Findings

- `ghostty_surface_config_s` includes `working_directory`, `command`, `env_vars`, `initial_input` and `wait_after_command`; the API exposes surface creation/free, `process_exited`, draw, focus, resize, key, text, paste, preedit, mouse and IME-point operations. The API also returns surface size, foreground PID and TTY name. [Surface config and size](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/include/ghostty.h#L474-L517), [surface API](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/include/ghostty.h#L1127-L1185)
- The C API reports actions, including child-exit and desktop-notification actions, and delegates wakeup, action, clipboard read, clipboard confirmation, clipboard write and surface-close handling through runtime callbacks. Clipboard request types explicitly distinguish OSC 52 reads and writes. The macOS platform config accepts an `NSView` pointer. [Callbacks and clipboard request types](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/include/ghostty.h#L90-L125), [runtime callbacks](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/include/ghostty.h#L474-L509), [actions and callbacks](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/include/ghostty.h#L950-L1072)
- OVRCR's checked-in Dashboard pushes Kitty keyboard flags with `CSI >15u` and pops its owned mode with `CSI <1u`; the source comments that the all-key mode needs alternate values to retain shifted punctuation. It also enables bracketed paste, mouse and focus reporting, and restores owned modes in the terminal guard. The project guide states the same exact input contract. [Terminal guard](../../crates/ovrcr-tui/src/dashboard/terminal_guard.rs#L12-L15), [TUI behavior guide](../../docs/development/tui.md#L89-L94)
- The `libghostty-vt` key encoder exposes Kitty flag bits for disambiguation, press/repeat/release, alternate keys, all keys and associated text; the constants define `REPORT_ALTERNATES` as bit 4, `REPORT_ALL` as bit 8 and associated text as bit 16. OVRCR's mask 15 is bits 1|2|4|8 and deliberately omits bit 16. The encoder can synchronize itself from a terminal's negotiated mode state. [Key encoder API](https://lib.ghostty.org/vt/group__key.html)
- `libghostty-vt` documents encoders for key, mouse, focus and paste input. Its terminal API tracks current Kitty keyboard flags and mouse modes. Ghostty's README lists Kitty graphics, clipboard sequences and synchronized rendering among its supported terminal sequences. [Input API](https://lib.ghostty.org/vt/group__api__input.html), [terminal API](https://lib.ghostty.org/vt/group__terminal.html), [Ghostty README](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/README.md#L64-L85)
- A real Swift/AppKit embedder, cmux, maps `NSEvent` through `ghostty_surface_key`. Its source routes marked composition through `ghostty_surface_preedit`; committed text received during `interpretKeyEvents` is accumulated and sent as a text-bearing `ghostty_surface_key` event (keycode 0, no modifiers), while out-of-keyDown committed text follows a separate typed-text path. [cmux key path](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/Sources/GhosttyTerminalView.swift#L7382-L7390), [cmux IME commit path](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/Sources/GhosttyTerminalView.swift#L7680-L7730), [cmux text-only key event](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/Sources/GhosttyTerminalView.swift#L14582-L14596), [cmux preedit path](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/Sources/GhosttyTerminalView.swift#L14846-L14865)
- The VT demo describes Unicode and multi-codepoint grapheme support but explicitly no glyph shaping or layout. Ghostty's macOS app uses Metal and CoreText. That makes full Ghostty a stronger base for ligatures, font fallback and native glyph rendering; `libghostty-vt` consumers must supply those presentation layers. [Ghostling demo](https://github.com/ghostty-org/ghostling/blob/main/README.md#features), [Ghostty README](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/README.md#L109-L118)
- cmux has a separate `GhosttyNSView+Accessibility.swift` integration file. The full C surface does not expose a high-level accessibility tree API, so accessibility must be verified in the host rather than assumed from terminal rendering. [cmux accessibility host source](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/Sources/GhosttyNSView%2BAccessibility.swift)
- In OVRCR's current source, `TERM=xterm-256color` appears in the shell-prompt probe, not as a general live-session default. The embedded Dashboard child and the server-launched session programs therefore need an explicit `TERM`/terminfo policy in the app packaging and launch path. [OVRCR shell-prompt probe](../../crates/ovrcr-runtime/src/session/shell_prompt.rs#L58-L64)

### Inferences

- Under the confirmed OVRCR contract, configure the full engine surface to run the bundled Dashboard command in a private outer PTY. The surface's child exit ends or restarts that Dashboard client; the Rust server remains the owner of live workspaces and session processes. The engine does not need an API to attach to OVRCR's already-owned inner PTYs for this design.
- The full engine can supply terminal parsing, rendering, font shaping and low-level protocol behavior, but AppKit still needs to translate physical `NSEvent` fields, modifier state, typed text, IME marked/committed text, focus and mouse events into the C surface API. The current Ghostty surface API itself accepts these values; it does not receive AppKit events automatically.
- The current cmux AppKit code is evidence that a full-engine host can route composition separately from Kitty associated-text reporting. It does not establish the bytes emitted by the engine for a text-only key event while `CSI >15u` is active. There is no confirmed failure, but exact-mask IME behavior remains an acceptance test.
- Product-specific `Cmd` bindings should be handled by the Swift host and terminal `Ctrl` events should reach the Dashboard. Ghostty's own surface key-binding configuration and Mac defaults make shortcut ownership a host decision, not something to accept implicitly.

### Gaps

- I did not run the full engine, libghostty-vt, cmux or OVRCR in a GUI or PTY. In particular, `ghostty_surface_process_exited`, `wait_after_command`, window-close behavior and restart policy are API evidence, not verified lifecycle semantics for an OVRCR child.
- Test Kitty mode mask 15 against the real Dashboard, especially CJK/emoji IME composition, committed text, shifted punctuation, alternate/base-layout keys, Ctrl shortcuts, key repeat and release. The cmux source exposes a committed-text path, but its source alone does not prove the PTY byte sequence.
- Verify OSC 52 writes and read/confirmation callbacks with OVRCR's copy flows; verify bracketed paste, focus, mouse reporting, resize, synchronized output, font zoom, selection, scrolling, ligatures, wide emoji, cursor placement and VoiceOver/accessibility text in the bundled host.
- Set and verify `TERM` and `TERMINFO` for the hosted Dashboard and for server-launched programs. The source review found no general OVRCR live-session `TERM` default, and no final app bundle/terminfo policy was inspected.

## What are the implementation, license and maintenance tradeoffs, and what is the decision gate?

### Takeaway

Full Ghostty has the best feature fit for the planned native terminal host, and a current Swift/AppKit product proves that a full-engine XCFramework can be built and shipped. That example does so by pinning a Ghostty fork and owning a build/artifact pipeline; it does not turn the upstream internal API into a supported dependency. Proceed only with an explicit willingness to maintain that pin/fork and its macOS build pipeline. Choose `libghostty-vt` if upstream support and ABI stability outweigh building the missing renderer and host behavior.

### Cited Findings

- cmux at inspected main commit `b9eda4f5...` points its `ghostty` submodule at `manaflow-ai/ghostty.git`, not upstream `ghostty-org/ghostty`; its pinned fork revision is `ef4f1570...`. The Swift package wraps a local `GhosttyKit.xcframework` binary target. [cmux `.gitmodules`](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/.gitmodules), [cmux package](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/Packages/Shared/CmuxGhosttyKit/Package.swift)
- cmux's dispatch-only workflow checks out the submodule, runs selected Ghostty tests and builds `GhosttyKit.xcframework` with Zig using `-Demit-xcframework=true`, `-Demit-macos-app=false`, `-Dxcframework-target=universal` and `-Doptimize=ReleaseFast`; it disables Sentry and i18n. Its ensure script fetches a prebuilt artifact only when that Ghostty SHA has a reviewed checksum, otherwise it rebuilds locally. [cmux build workflow](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/.github/workflows/build-ghosttykit.yml), [cmux artifact verification/build script](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/scripts/ensure-ghosttykit.sh)
- cmux separately carries Ghostty runtime resources, including theme and terminfo directories. The XCFramework alone is therefore not the whole terminal bundle. [cmux Ghostty resources](https://github.com/manaflow-ai/cmux/tree/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/Resources/ghostty), [cmux terminfo overlay](https://github.com/manaflow-ai/cmux/tree/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/Resources/terminfo-overlay)
- Ghostty's license is MIT. cmux's root `LICENSE` is GPL-3.0-or-later for its independently authored host code, while its third-party license list names Ghostty as MIT. Reusing Ghostty under its license is distinct from copying cmux's host implementation. [Ghostty license](https://github.com/ghostty-org/ghostty/blob/46f1cea1a10a19bef97a8a0f5948e660d0b74fe2/LICENSE), [cmux license](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/LICENSE), [cmux third-party notices](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/THIRD_PARTY_LICENSES.md)
- The `libghostty-vt` Swift package route is a published static XCFramework with checksum instructions and a stable C ABI from 1.0. Building its source needs Zig 0.17; consuming its prebuilt Swift XCFramework avoids building Ghostty from source. It still does not provide PTY management or drawing. [Swift XCFramework installation](https://lib.ghostty.org/vt/installing.html), [tagged ABI note](https://github.com/ghostty-org/ghostty/blob/vt-1.0.1/include/ghostty/vt.h#L1-L13), [terminal API responsibilities](https://lib.ghostty.org/vt/group__terminal.html)
- The cmux example uses a fork pinned several weeks behind the inspected Ghostty `main` revision and builds a custom flavor. This is direct evidence of a maintained integration path and also evidence that downstream version/resource/build maintenance is part of the solution. [cmux submodule pin](https://github.com/manaflow-ai/cmux/tree/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/ghostty), [cmux build flavor and pinning](https://github.com/manaflow-ai/cmux/blob/b9eda4f5b5398edf3a1b8da7e7a3363bf3488a75/.github/workflows/build-ghosttykit.yml)

### Inferences

- **Recommendation:** go to a bounded feasibility spike with the full engine only if OVRCR is prepared to pin a Ghostty revision, own or maintain a fork, build/checksum the XCFramework, package the required resources and revalidate on upstream changes. Do not treat full `libghostty` as a stable drop-in library today.
- **Alternative:** go with `libghostty-vt` if the project prefers a published Swift binary and stable C ABI; budget for OVRCR to own Metal/CoreText rendering, font shaping, selection/scrolling, accessibility and full AppKit IME/key input handling.
- The MIT Ghostty engine can be evaluated independently of cmux host code. cmux is useful as an implementation reference and proof of build feasibility; its GPL host code should not be copied without an explicit licensing decision.
- The engine's upstream app downloads are signed/notarized, but no upstream full-engine external XCFramework distribution/signing contract was found. OVRCR would need to pin artifact provenance and validate signing/notarization of its final `.app`; this audit did not inspect OVRCR's future packaging pipeline. [Ghostty macOS binary distribution](https://ghostty.org/docs/install/binary)

### Gaps

- Before deciding on the full engine, reproduce a source-pinned `GhosttyKit.xcframework` build for arm64 and x86_64 on the intended macOS baseline, package runtime resources/terminfo, verify codesigning/notarization, and measure clean build/rebuild cost. The upstream internal API has no published macOS minimum or architecture contract.
- Run an actual Swift `.app` against an isolated OVRCR server: launch the Dashboard through a surface command, confirm one active Dashboard and the 50-session limit, close the window while server notifications continue, quit with Cmd-Q and confirm the Rust sessions detach rather than terminate, then relaunch after normal child exit and crash.
- CUA acceptance must cover the exact Kitty keyboard mode stack (push `>15u`, restore `<1u`), `TERM`/terminfo, input composition, OSC 52, bracketed paste, focus, mouse, resize, selection/scrollback, Unicode/emoji/ligatures, font zoom, accessibility and the Cmd-versus-Ctrl shortcut contract.
- No prototype, install, test or GUI run was performed for this research-only task. Confidence is high on the source/API distinction and cmux build precedent, medium on protocol fit from API/source inspection, and low until the exact OVRCR AppKit/PTY lifecycle, IME and accessibility acceptance passes.
