## Production contract and actual workload

### Takeaway

The embedded terminal view is one outer PTY and one OVRCR Dashboard grid. OVRCR’s Server continues to own provider PTYs and their terminal parsers. Supporting 50 live sessions therefore does not mean creating 50 native terminal views; the Dashboard can show at most four pane grids, further limited by window geometry. [event_loop.rs:39-107](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/event_loop.rs#L39-L107), [server/mod.rs:256](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-runtime/src/server/mod.rs#L256), [dashboard.rs:1-38](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-runtime/src/server/dashboard.rs#L1-L38), [dashboard/mod.rs:118-137, 157, 449-497](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/mod.rs#L118-L137).

### Cited findings

- With no CLI subcommand, startup connects to the Server and calls `run_dashboard`. That function reads terminal rows/columns, creates one Ratatui `Terminal<CrosstermBackend<_>>`, and reads input from stdin or `/dev/tty`. The embedded app must provide one real PTY to the Dashboard process and relay its bytes and size changes. [cli/mod.rs:71-80](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/src/cli/mod.rs#L71-L80), [event_loop.rs:39-100, 703-713, 854-860](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/event_loop.rs#L39-L100).
- The Server enforces one active Dashboard owner and a 50-live-session limit. Each live session gets its own `portable-pty` pair and `vt100` parser on the Server side. The Dashboard’s pane layout caps at four and draws only geometry that fits, collapsing to the focused pane when the full layout does not fit. [server/dashboard.rs:1-38](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-runtime/src/server/dashboard.rs#L1-L38), [server/mod.rs:256, 1223-1227](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-runtime/src/server/mod.rs#L256), [session/mod.rs:568-575, 703-714](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-runtime/src/session/mod.rs#L568-L575), [dashboard/mod.rs:157, 449-497](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/mod.rs#L157-L497).
- Server PTY bytes are parsed into per-session screens. `screen_window` exposes rows from the Server’s retained history; when a provider is in its alternate screen, that history view reports zero scrollback rows. The Dashboard renders cell screens into its own Ratatui grid. Its native History and Copy behavior therefore remains OVRCR-owned; the host terminal’s scrollback is not a substitute for it. [session/mod.rs:966-975, 1107-1174](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-runtime/src/session/mod.rs#L966-L975), [render.rs:70-124](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/render.rs#L70-L124).
- At Dashboard entry, `TerminalGuard` enters the alternate screen, pushes Kitty keyboard flags with `CSI >15u`, enables bracketed paste, mouse capture and focus reporting, and hides the cursor. Cleanup pops one keyboard mode and restores the cursor, screen, paste, mouse, focus and raw mode. It does not enable synchronized output (2026). [terminal_guard.rs:10-12, 66-84, 105-131](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/terminal_guard.rs#L10-L12).
- OVRCR requests flags 1|2|4|8 (disambiguation, event types, alternate key values, all-key reporting); it does not request flag 16 (associated text). The Kitty protocol specification says associated text is a separate progressive enhancement. crossterm 0.29 has no text field on `KeyEvent`, marks associated-text support as unimplemented, and ignores bit 16 in its flag query parser. [terminal_guard.rs:10-12, 66-84](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/terminal_guard.rs#L10-L12), [crossterm event.rs:284-310, 934-953](https://github.com/crossterm-rs/crossterm/blob/v0.29.0/src/event.rs#L284-L310), [crossterm Unix parser:283-286](https://github.com/crossterm-rs/crossterm/blob/v0.29.0/src/event/sys/unix/parse.rs#L283-L286), [Kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/).
- Plain UTF-8 received from the terminal is parsed by crossterm as `KeyCode::Char`; the Operator Quick editor inserts those characters. The SwiftTerm main-branch AppKit path reported in this pass routes committed IME text as raw UTF-8 when flag 8 is active without flag 16. That is consumable by OVRCR, but exact mask-15 composition behavior still needs a real-host check. [crossterm Unix parser:118-124](https://github.com/crossterm-rs/crossterm/blob/v0.29.0/src/event/sys/unix/parse.rs#L118-L124), [operator.rs:452-499](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/operator.rs#L452-L499), [SwiftTerm main at d4f52faa](https://github.com/migueldeicaza/SwiftTerm/commit/d4f52faaae413b2e69c728ad79cd225cdbebc042).
- Enhanced keys are not a blocker to launching the Dashboard: ordinary character and control events are handled, and Ctrl-g accepts either a control-modified `g` or BEL. They are needed for complete key distinctions: OVRCR’s guide explicitly requires alternate key values so shifted punctuation such as `:` and `?` remains the character typed, and Operator Quick uses Shift+Enter for newline versus bare Enter for submit. [input.rs:6-45](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/input.rs#L6-L45), [keymap.rs:242-247](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/keymap.rs#L242-L247), [operator.rs:473-499](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/operator.rs#L473-L499), [TUI guide:88-92](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/docs/development/tui.md#L88-L92).
- Mouse capture changes with Dashboard mode; terminal mouse events are forwarded with cell-relative SGR/legacy coordinates. Copy writes OSC 52 with a 64 KiB UTF-8 limit. [event_loop.rs:332-348](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/event_loop.rs#L332-L348), [input.rs:58-96](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/input.rs#L58-L96), [copy.rs:630-641](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-tui/src/dashboard/copy.rs#L630-L641).
- The development egui harness is an outer terminal test, not a production native Dashboard. It launches the real Dashboard in one PTY, parses its ANSI output with `vt100`, and sets `TERM=xterm-256color` and `COLORTERM=truecolor` for the TUI child. Its renderer has CJK/emoji width and missing-glyph checks and exposes each non-empty row to egui accessibility. Production session command construction does not explicitly set `TERM` or `COLORTERM` in its spawn block. [src/gui.rs:1, 359-385, 473-503](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/src/gui.rs#L1-L1), [ovrcr-gui.rs:265-295, 565-578](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/src/bin/ovrcr-gui.rs#L265-L295), [session/mod.rs:577-620](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/crates/ovrcr-runtime/src/session/mod.rs#L577-L620).

### Inferences

- Keep the embedded host to one terminal view for the Dashboard process. Keep the Server as the owner of all inner provider PTYs; the host should relay terminal input, output, focus and resize to the Dashboard process rather than create one engine instance per session.
- The engine must handle the Dashboard’s own alternate-screen and cursor lifecycle, truecolor/256-color cells, cell-width behavior, paste, focus events, dynamic mouse capture and OSC 52. The app’s built-in History/Copy modes and pane scrolling remain separate UI behavior. A native terminal scrollbar cannot replace them. Any claim of pixel-smooth scrolling must be evaluated in the actual AppKit/WebKit event and rendering path.
- Kitty flag 16 is not currently consumable as associated text by crossterm. If an engine emits IME text only as associated-text CSI-u sequences, the current input path cannot consume it; either preserve the engine’s separate raw UTF-8 text path or change the TUI/input contract. This is a compatibility gate, not proof that SwiftTerm or Ghostty loses IME text.

### Gaps

- Verify that production Server-launched provider PTYs receive a useful `TERM`/`COLORTERM` and that packaged terminfo exists; only the egui harness’s Dashboard child explicitly gets these variables.
- Native engine tests have not established exact `CSI >15u` push/pop behavior, mask-15 IME commits, focus reports, OSC 52 permissions, selection behavior, VoiceOver exposure, or resizing on font zoom. No comparative performance evidence was collected.
- A 50-session workload means up to 50 Server PTYs/parsers and output producers, but only one outer Dashboard stream and at most four visible pane grids. Performance under 50 simultaneous heavy writers remains unmeasured.

## Alternative engines and ranking

### Takeaway

SwiftTerm is the strongest direct native-view candidate. xterm.js in WKWebView is a credible fallback if the native bridge and IME gates pass. Ghostty’s official `libghostty-vt` is a credible terminal-state library, but not a drop-in Swift view; the full GUI API is not maintained as an external embedding API. libvterm and OVRCR’s vt100/egui path are effort controls, not lower-work replacements.

### Cited findings

- **1. SwiftTerm — first candidate, conditional on release pin and host tests.** The project describes an embeddable Swift terminal library with AppKit/UIKit frontends and an MIT license. GitHub’s latest release at research time was v1.99.3 (2026-11-06); the current main commit was d4f52faa (2026-11-12). Main-branch code reported in this pass implements OVRCR’s Kitty flags 1/2/4/8 and routes AppKit `insertText` commits through raw UTF-8 when associated-text flag 16 is absent. The main-branch behavior is newer than the latest release tag, so verify the pinned release or pin the commit explicitly. [SwiftTerm repository](https://github.com/migueldeicaza/SwiftTerm), [v1.99.3 release](https://github.com/migueldeicaza/SwiftTerm/releases/tag/v1.99.3), [main commit d4f52faa](https://github.com/migueldeicaza/SwiftTerm/commit/d4f52faaae413b2e69c728ad79cd225cdbebc042).
- **2. xterm.js in WKWebView — credible fallback, conditional.** The latest stable release was 6.0.0 (2025-12-22); its tagged public typings do not expose the Kitty keyboard option that current main adds as opt-in `vtExtensions.kittyKeyboard` (default false). A reported open issue documents single-CJK-character IME commits being dropped with Kitty mode in xterm.js 6.1.0-beta.285 on Linux/X11; this is a specific report, not proof about WKWebView or all IMEs. A WKWebView host would still need a native PTY/process bridge, local bundled assets, CSP, resize and clipboard plumbing; no performance claim was found. [6.0.0 release](https://github.com/xtermjs/xterm.js/releases/tag/6.0.0), [6.0.0 typings](https://github.com/xtermjs/xterm.js/blob/6.0.0/typings/xterm.d.ts), [current-main typings](https://github.com/xtermjs/xterm.js/blob/master/typings/xterm.d.ts), [IME issue #6112](https://github.com/xtermjs/xterm.js/issues/6112), [xterm.js addon API](https://xtermjs.org/docs/guides/using-addons/).
- **3. Ghostty `libghostty-vt` — viable only with custom AppKit rendering and I/O.** Official docs publish a Swift-importable XCFramework and describe a C API for terminal parsing/state. The Ghostty 1.4 release notes say libghostty-vt is separate from the Ghostty GUI release. A maintainer describes the full `libghostty.h` API as “libghostty-internal,” designed around Ghostty’s macOS app, and advises external projects to maintain a fork rather than expect new embedder APIs. Thus the published VT library is a credible parser/state core, while the full Ghostty GUI library is not a stable drop-in host view. [libghostty-vt install docs](https://lib.ghostty.org/vt/installing.html), [Ghostty 1.4 release notes](https://ghostty.org/docs/install/release-notes/1-4-0), [maintainer answer in discussion #14360](https://github.com/ghostty-org/ghostty/discussions/14360).
- **4. libvterm or OVRCR vt100/egui — effort controls.** The Neovim `libvterm` fork is MIT-licensed terminal-state code, not an AppKit view or PTY manager. OVRCR already owns a locally patched vt100 0.16.2 parser and a development egui outer-terminal implementation; that harness proves a test path exists, not that its rendering, IME, selection, accessibility and lifecycle work is a production-quality terminal host. [neovim/libvterm](https://github.com/neovim/libvterm), [OVRCR GUI harness](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/src/gui.rs#L1-L1), [OVRCR vt100 lock entry](https://github.com/xlyk/ovrcr/blob/56ef7694318b5a1ec0514424b503dd2d004ff6a1/Cargo.lock#L4598-L4602).
- iTerm2, WezTerm and Alacritty are terminal applications, not comparable in-process view libraries for the Swift host; they are out of this embedded-engine ranking. [iTerm2](https://iterm2.com/), [WezTerm](https://wezterm.org/), [Alacritty](https://alacritty.org/).

### Inferences

- Start with a pinned SwiftTerm release/commit if its `TerminalView` passes the OVRCR matrix below. Keep xterm.js as the web-rendered fallback if SwiftTerm cannot meet native text/IME requirements and the WKWebView bridge is acceptable. Choose `libghostty-vt` only if a custom AppKit renderer is intentional; do not take the full internal Ghostty GUI API as a supported SDK.
- Exclude an engine if it cannot preserve OVRCR’s one active Dashboard, mode restoration, raw UTF-8 IME path, OSC 52 copy, visible-cell resize, and keyboard distinction behavior. A terminal parser alone does not satisfy the host requirement.

### Gaps

- SwiftTerm’s v1.99.3 tag versus its d4f52faa main branch needs an exact feature check; no native-window walkthrough or release-tag compatibility test was run.
- xterm.js 6.1 release status and the disposition of issue #6112 were not verified beyond the official release list and open issue state observed on 2026-11-13.
- Ghostty’s XCFramework is a VT core; this scan did not validate a Swift terminal view package built on it. No engine memory, CPU, scrolling-smoothness or 50-session benchmark was collected.
