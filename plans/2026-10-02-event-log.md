# Event log (item 6 of the usage-defaults plan)

Decided with Kyle on 2026-10-02 over three grilling rounds. Vocabulary in `CONTEXT.md`: Event, Quota reason. Decision record: `docs/adr/0009-durable-events.md`.

## Problem

The Server has no log crate and writes only `eprintln!` lines to stderr, which land in `server.log` beside the socket, or in `.service.log` and `.service.err.log` beside `config.toml` under the installed service. The title worker decides silently (no model, Pi missing, history unchanged, call failed, another call in flight), so a session that was never titled cannot be explained from the Dashboard. Quota reasons (#253) and settings findings (#249) are the first OVRCR-written one-line explanations, and they live only in their own popups.

## Decisions

1. An Event is one dated, OVRCR-written line about a decision the Server made or a state it changed: component (`titles`, `settings`, `quota`, later `provisioning` and `sessions`), time, the session or provider concerned, and a one-line message under the same rule as a Quota reason: never a prompt, a transcript, a credential, an account identifier or a native body.
2. The Server keeps a bounded in-memory ring (2000 events) and publishes each new event to the attached Dashboard. stderr keeps today's lines unchanged.
3. The Server also appends every event to `events.jsonl` beside the instance identity (a fixed sibling name like `dashboard.toml`), one JSON event per line, mode 0600, capped at 5 MB with one rotation to `events.jsonl.1`; old lines are never rewritten. The file is for people and other tools and survives a Server restart.
4. First emitters: titles (for each session, why it was or was not titled on each tick that mattered: no `title_model`, Pi missing for this model, history unchanged, call sent, call failed: <reason> or call timed out after <N>s, title applied or dismissed); settings (reload, findings count, each `SetSetting` write and refusal); quota (every state transition with its reason, each refresh and cooldown refusal). Provisioning and session lifecycle later, each as its own small PR.
5. Surfaces: an Events popup from the menu and the palette (newest last, scrollable, a `/` word filter, a component filter), and `ovrcr events [--follow] [--json]` through a Server request. Both need a running Server; the CLI does not read the file.
6. Out of scope: replacing every `eprintln!`, a log level system, log shipping, reading the file from the CLI, events from the Dashboard process itself.

## Delivery: two PRs, after wave 4

PR 1: the event type on the wire, the Server ring, the file writer with its cap and rotation, the titles, settings and quota emitters, `ovrcr events`, ADR 0009, docs (`docs/development/runtime.md`, `docs/cli-reference.md`, README paths table). Acceptance: each emitter yields the specified events under its existing fixtures (a session titled and one not titled for each reason; a settings reload with findings and a `SetSetting` refusal; a quota state transition, a refresh and a cooldown refusal); the ring drops the oldest at 2000; the file rotates once at the cap and never loses a whole event; `ovrcr events --json` round-trips; no event message contains any byte of a fixture prompt, transcript, native body or the auth-status fixture's email.

PR 2: the Dashboard popup with filters, live append while open, and CUA evidence per `docs/testing-computer-use.md`; `docs/dashboard.md`.
