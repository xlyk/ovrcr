# One settings document, read only by the Server

Decided 2026-10-01, from the shared-configuration grilling for the usage-defaults work.

Every setting lives in one settings document, `dashboard.toml` beside the instance identity. `config.toml` stays the instance identity only: it names the database, task store and socket, and a `[quota]` table found there is a finding, not configuration. The Server is the one process that reads the document. It loads every setting at startup, re-reads when the file changes, and publishes a settings snapshot (effective values, sources, findings, document path, read time) to the Dashboard at hello and on every change. The Dashboard has no parser of its own. The Server is also the only writer: the Dashboard and the CLI change a value by sending the Server a setting path and TOML value text, and the Server validates it against the declared type, edits the document in place (comments and unrelated keys preserved), re-reads and republishes. The CLI writes the document itself only when no Server is running.

A bad value defaults only its own setting and yields a finding; an unknown key or spelling yields a finding; only an unparseable document falls back to all defaults, loudly. No settings mistake prevents the Server from starting or a Dashboard from attaching. Settings that spend money, touch credentials, expose data or need an OS permission are consent settings: off until set, and their off state says what to set.

Rejected: a parser per process (the Server read `title_model`, `automatic_local_terminals` and `[quota]` with three different loaders while the Dashboard had a fourth, so one file could mean different things to the client and the service, and one wrong type reset every Dashboard preference); a per-setting environment layer (nothing needs it and it doubles the source model); a file-watch dependency (a two-second stat on an existing Server tick is enough).
