# Operator Layout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the selected Original layout: Operator conversations in the existing sidebar, a readable native conversation view, close/archive, and an app-wide quick-message dialog.

**Architecture:** Keep `dashboard::operator::Hub` as the owner of conversation UI state and use the existing Server, retained journal and exact-run lifecycle controls. Extend the shared sidebar geometry and current input dispatcher rather than building another navigator. Use the existing Create/Submit protocol for quick messages; add a native Close operation and authoritative retained-run metadata for archive/restore.

**Tech Stack:** Rust 2024 / Rust 1.97.1 minimum, existing Ratatui 0.30, Crossterm 0.29, protocol framing and SQLite SessionStore. No new dependency, worker framework or credential flow.

**Spec:** [Selected design and requirements](../../ux/2026-10-30/operator/README.md), [mockup source](../../ux/2026-10-30/operator/mockups.fragment.html), and the preserved [Operator product contract](../specs/2026-10-29-rig-operator-design.md). This plan changes the layout and creation entry points described by the older contract.

**Baseline:** `24cdc917afdf95c52505420dd4affe7bf0c64b02` on `codex/operator-layout-design`; its Operator implementation base is `aef3e7f0f1c6a498f2b9fa2d1cc17f83883439b8`. Recheck branch drift before execution. This document authorizes no implementation by itself.

## Global Constraints

- Operator manages OVRCR projects, workspaces and sessions. Original layout is selected; do not implement the other eight alternatives or their session-preview/dock features.
- One synchronous Server owner, one active Dashboard, fifty total live-session slots. Preserve concurrent conversations and one active turn per conversation.
- Put Operator and its conversations above Projects in the existing left sidebar. Each conversation occupies exactly one line; no model label appears there.
- Reuse the green busy spinner, teal unread `✓`, normal-weight titles, selected background/leading mauve `▌`, hover `[x]`, uppercase heading/rule and collapsed `▸ count`.
- Close means confirmed exact-run termination followed by archive, preserving the journal and model history. Keep generic terminal kill/close refusal for Operator; permanent history deletion is outside this change.
- Captured contexts include stable workspace/session/run identities. Navigation and delayed responses must not retarget accepted work or overwrite another draft.
- Ctrl+O is reserved app-wide within OVRCR, including terminal input. Keep a clickable entry in the title bar and sidebar `[+]`; preserve the existing manual provider/model creation path.
- Enter starts a new conversation and sends its first message; Shift+Enter inserts a newline; paste never submits; whitespace cannot submit. Use configured provider/model defaults for this quick path.
- Esc before Enter creates nothing. After Enter it dismisses the popup, without cancelling accepted Create/Submit or allowing a late response to steal focus. No automatic retry of an ambiguous mutation.
- Preserve text/control escaping, grapheme editing, durable-tail Unread acknowledgement, process-stop proof, input/view handshakes and content-free operational logs.
- Native layout baseline: 80×24 and 60 columns. Operator view/dialog minimum: 60×16. Keep terminal-mode behavior outside Operator intact.
- Tests use private HOME/config/socket/workspaces/provider fixtures. No personal credentials, real account calls, paid inference, installed binary replacement or live-session changes.

## Review Focus

1. A→B→A navigation with late List/Created/Submitted/Closed responses must preserve the active view, captured target, draft and monotonic retained-run authority. Tasks 1, 2 and 4 pin this ordering.
2. A quick dialog above Tasks, History, Copy or a pending WIP-save confirmation must own keyboard, paste and mouse input; Esc must never answer the underlying confirmation. Task 4 covers the production entry points.
3. Close during a running tool, stop failure or Dashboard-owner replacement must not archive uncertain work, affect another conversation, or lose the journal. Tasks 1 and 5 cover real process groups.
4. Resize, hidden panes, collapsed sections, paged history and covered transcripts must never mark an unseen durable reply reviewed. Tasks 2, 3 and 4 cover rendering and acknowledgement together.
5. Wide/combining glyphs, ANSI/bidi controls, multiline paste, long titles/paths and large conversation lists must remain editable and bounded without leaking PTY input. Tasks 2–5 cover state, frames and real input.
