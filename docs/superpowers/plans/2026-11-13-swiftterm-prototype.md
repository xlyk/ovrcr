# SwiftTerm prototype MVP and implementation plan

**Decision to make:** Can one native Mac terminal view run OVRCR’s existing Rust Dashboard and feel good enough to keep using it for daily typing, reading, and switching sessions? The prototype is a development-only macOS app. Its success earns SwiftTerm a place in the next app milestone. Production adoption still depends on the [full comparison and acceptance matrix](<../../../reports/OVRCR embedded terminal options.md>).

For the subsequent build, native test results, and remaining adoption checks, see the [prototype progress report](../../../reports/swiftterm-prototype-progress.md).

## What counts as the MVP

From a checkout, a developer runs one command and gets a resizable Mac window showing the real Dashboard with disposable local shell sessions. They can edit an Operator Quick draft using a macOS input source, switch to a shell, interrupt a command, copy text through both the native selection and Dashboard Copy mode, and zoom the text without losing their place. A second shell produces output during these interactions. Closing and reopening the window restores the same Dashboard. Quitting releases the Dashboard connection and leaves the same shells available to another Dashboard.

Use one AppKit window and one SwiftTerm `LocalProcessTerminalView`. Its outer PTY runs the checkout’s `ovrcr` executable **with no subcommand**. The Rust Dashboard draws every pane into that view. The independent Rust Server owns the inner session PTYs. Start with SwiftTerm’s default CoreText rendering path and the exact [researched SwiftTerm revision](https://github.com/migueldeicaza/SwiftTerm/commit/d4f52faaae413b2e69c728ad79cd225cdbebc042). This pin includes the macOS held-key repeat change.

The MVP needs a local development bundle, a single Mac, and evidence from the real window. Notification delivery and click-through, distribution signing, installation and updates, other Mac architectures, and sustained output across all 50 sessions belong to later milestones. Keep those rows open in the full matrix. A renderer comparison or port to Ghostty becomes useful only if this experiment identifies a SwiftTerm limitation.

## Implementation order

1. **Launch the real Dashboard safely.** Add a macOS-only Swift package under `experiments/swiftterm/`, pin SwiftTerm by revision, and provide a single development command such as `just swiftterm-prototype`. The launcher builds one matching Rust CLI, places it in the development app bundle, and uses that image for both the Server and Dashboard. Run against a fresh private HOME, OVRCR home, socket, config, and temporary Git workspace with local shells. Use the existing fixture setup where practical. The Rust GUI demo already has a separable lifetime: a developer runner can hold `Demo::start` while the Swift window attaches to its socket. Leave `Demo::dashboard` to the egui helper because that method already allocates an outer PTY. Propagate the fixture environment, explicitly set `OVRCR_SERVER_EXECUTABLE`, clear inherited config/provider overrides, and supply a known working directory and verified `TERM`/terminfo. Launch by absolute path. If the fixture or executable is missing, show a launch error and stop before resolving a default instance. See [GUI fixture](../../../src/gui.rs), [CLI entry point](../../../src/cli/mod.rs), and [GUI helper lifecycle](../../gui-helper.md).

2. **Get one working vertical slice before adding shortcuts.** Create one window, make the terminal its first responder, and use SwiftTerm’s local-process support for byte transport and resize. Show the child’s exit or attach refusal without starting another Dashboard. Prove the slice by selecting an existing shell in the Dashboard, typing a command whose output differs from its echo, then resizing and reading the new `stty size` in that shell. Stop here to diagnose a failed input or resize path before adding app behavior.

3. **Wire the Mac interactions that decide engine fit.** Route Cmd-C/V to native selection and paste, and Cmd-plus/minus/0 to font size and reset. Recompute the cell grid on zoom. Leave Ctrl-C, Ctrl-G, Return, modified Return, mouse reporting, bracketed paste, and IME on the existing terminal path. Configure Option so the native dead-key check can run. Use the view’s public hooks for Dashboard OSC 52 clipboard writes, preserving OVRCR’s 64 KiB bound. User-initiated Cmd-V supplies pasteboard input. Agree on one selection gesture that works when the Dashboard captures the mouse, and record it in the prototype instructions. Exercise the default renderer before considering Metal. See [keyboard setup](../../../crates/ovrcr-tui/src/dashboard/terminal_guard.rs), [Dashboard Copy](../../../crates/ovrcr-tui/src/dashboard/copy.rs), and [SwiftTerm input and clipboard notes](<../../../research_notes/OVRCR embedded terminal options/swiftterm.md>).

4. **Separate window, Dashboard, and fixture lifetimes.** Cmd-W hides the window and retains the same view and child. Dock reopen restores focus to that view. Cmd-Q ends and reaps only the app’s Dashboard child. The runner keeps the fixture Server alive long enough to exercise CLI reattachment after quit, then shuts down only its own fixture on explicit teardown. Refuse to tear down a root or socket whose ownership cannot be established. Exercise both a second-Dashboard refusal and a quit during active shell output.

5. **Run the acceptance session and record the verdict.** Add one focused test for host policy, such as refusal to launch with a missing fixture, and an integration test through the normal bundle/fixture path for attach, quit, session survival, and reattach. Run the remaining checks below through the actual Swift window using the repo’s [native computer-use procedure](../../testing-computer-use.md). Use a real macOS input source for composition and VoiceOver for the reading check. A pasted Unicode string exercises a different code path. Save the run command, both revisions, Mac/OS/toolchain and input source, actual vs. expected results, and fixture cleanup outcome. Keep screenshots of native composition and the resized grid, accessibility output, and a short CLI transcript with session IDs and sizes.

## Prototype acceptance

| Check | Action and observable pass condition |
|---|---|
| Real TUI and keyboard | Navigate Browse → Terminal → Browse using Return and Ctrl-G. Ctrl-C interrupts a running shell command and the shell still accepts input. With the Dashboard’s existing Kitty mask 15, type shifted punctuation and hold and release a character. The right characters appear, repeat stops on release, and Cmd actions inject no stray characters. In Quick, Shift-Return inserts exactly one newline and ordinary Return takes the submit path once. Use a local scripted provider or captured local submission for that last check. |
| Native text input | With a Japanese or Korean IME, compose mid-line in an unsent Quick draft and in a focused shell while a second pane redraws. Move the caret during composition, cancel once, and commit a multi-character phrase once. The candidate/marked text follows the caret, adjacent cells stay visible, cancellation leaves the original text intact, and the committed text matches exactly once. Repeat with an Option dead-key accent. Check real shell output or copied draft text as well as the visible overlay. |
| Drawing, zoom, and reading | Display box borders, truecolor, CJK, a combining accent, and emoji in a known fixture line. Zoom in, out, and reset. Borders align, the cursor lands after the expected cells, and text stays crisp at each size. Switch between two visible panes and resize during output. Each selected shell reports the expected inner pane dimensions, and typing after the resize reaches the selected pane. With VoiceOver, focus the view and read back a known line of terminal content. |
| Selection, clipboard, and scrolling | Copy a known Unicode selection with Cmd-C, then copy a different string from Dashboard History/Copy. Check each in the actual pasteboard. Cmd-V a multiline sample into Quick and confirm it stays one unsent draft with the expected line breaks. Scroll in History and return to the live session at its current output. Native selection must leave ordinary pane clicks and scrolling usable. |
| Ownership and recovery | Record Server and shell identity and a marker held only in shell memory. Hide and reopen the window during output and confirm the selection and marker survive. While hidden, an ordinary CLI list succeeds and a second interactive Dashboard is refused. After Cmd-Q, attach a real Dashboard through a test PTY to the same socket, verify the same shell identity and marker, detach, and reopen the Swift app. Confirm fixture teardown afterwards. |

**Proceed** when every prototype row passes on the recorded pin and the person doing the walkthrough can compose, read, and select text comfortably while output updates. **Hold** if a check was unavailable or a small host integration defect needs a fix and rerun. **Reconsider SwiftTerm** if a required input, rendering, or accessibility defect reproduces on that pin through the public view after checking the host wiring. Save the smallest reproduction and use it as the first test of full Ghostty. The next milestone still owns notification lifecycle, release packaging, broader IME and clipboard coverage, and the 50-session load test.
