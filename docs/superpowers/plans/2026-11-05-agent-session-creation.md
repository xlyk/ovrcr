## 2. Extend the existing launch path and settings, with tests through real entry points

Affected owners include protocol `wire.rs` (`CreateSessionRequest`, `SessionLaunch`), TUI `AgentEntry`/selection, runtime spawn/managed invocation, and typed settings catalog/loader. Current launch values are argv/label/kind; model and prompt are not structured fields today.

- Add only the structured options needed by the proven provider contracts and validate at the Server trust boundary. Update every constructor, exhaustive match, CLI/caller/fixture and wire compatibility requirement together.
- Route bounded discovery outside the input reader and lifecycle mutation locks; use existing request correlation/ownership patterns. Do not add a second model/provider authority, framework, SDK or settings parser to solve the form.
- Put ephemeral initial-prompt ownership with the exact Server session/run. Preserve pending text across Dashboard reconnects; never serialize text into ordinary retained metadata, settings or Events. Define known refusal versus unknown delivery, with no automatic uncertain replay.
- Extend successful per-project launch memory with model-policy selection through the existing settings owner. Keep Terminal memory and one-off command exclusion intact.

### Dashboard capability and pending-launch contracts (F5)

- Add a current-Dashboard capability query for a resolved launch configuration. The Server resolves/verifies the selected configuration against the actual executable/argv and its detected, configured or cloud-account origin; the response binds capabilities and models to that configuration. A changed/unavailable configuration invalidates an old response before Start. Do not use a display-name match as proof or call the authenticated delegation endpoint with a fabricated session. Extract reusable provider discovery primitives below the authority-specific entry points instead.
- Add a connection-independent launch-intent identifier to the new Dashboard launch path, using an existing ID-generation mechanism. Before accepting a prompt-bearing launch, the Server retains its frozen target/options/prompt in memory under that intent; after allocation it binds the same record to the exact session/run. Use the existing lifecycle/mutation owner for the effect, not a second launch scheduler. A repeated accepted intent must reconcile its status rather than spawn/send again.
- Provide a bounded, current-Dashboard read/reconciliation request for those Server-held intents, discoverable after reconnect without knowing the old connection's request token. Return the workspace/session/run target and known pending/accepted/refused/unknown state; return recoverable draft text only where delivery is known not to have happened. This is not a general read into another provider's conversation. Keep prompt-bearing wire Debug/error paths redacted.
- Retain pending text only for the current launch/run and Server lifetime, bounded by existing live-session/lifecycle admission. Clear accepted/retired text at the actual contract boundary. Missing state after restart or retirement means unavailable/unknown, not proof of non-delivery; never trigger automatic resend from absence. Do not add durable prompt storage to implement reconnect recovery.
- Test the new query and launch paths through their actual Dashboard authorization and dispatcher, including stale configuration, old run, duplicate intent, lost response and reconnect. A view handshake or response-cycle Ready is not native prompt acceptance.

### Wire and settings compatibility (F6)

- Update affected wire constructors/callers and the exact `wire_encoding_matches_snapshot_for_protocol_version` test in `crates/ovrcr-protocol/src/wire.rs`; bump `PROTOCOL_VERSION` in `codec.rs` when encoding changes. Preserve the existing explicit protocol-mismatch refusal rather than attempting to decode new fields as old messages. Confirm matching new client/server behavior and rejection of an incompatible client.
- Extend `launch_choices` deliberately across protocol `settings.rs`, runtime `settings/mod.rs` (including its current `{kind,preset}`/unknown-field parser), protocol `catalog.rs`, TUI `settings_editor.rs`, write fixtures and `settings_matrix.rs`. Existing Agent/Terminal settings remain readable; absence of a model policy means Harness default, not a guessed concrete model. Round-trip new explicit/default policies through the loader, writer and editor; preserve successful-only writes and one-off command exclusion.

Exit: real request→validation→provider launch paths demonstrate explicit/default model behavior and prompt blank/delivery/refusal/reconnect/restart semantics. Cover invalid/stale targets, capability changes, configuration overrides and missing models without silent fallback.

## 3. Implement the two dialogs using current Dashboard and lifecycle mechanisms

Primary owners: `dashboard/palette.rs`, `dashboard/lifecycle_ui.rs`, `dashboard/keymap.rs`, the hierarchy/workspace pickers and existing lifecycle completion handling in `server/mod.rs`.

- Build Branch-picker membership from the registry in the existing `Request::Inspect` / `Response::Inventory` path, joined to current hierarchy labels by project + workspace ID (F2). Hierarchy presence alone is insufficient: retained sessions synthesize rows without registry membership. Preserve a registered-but-unavailable checkout as an unavailable choice; exclude retained-only synthetic rows even if their label/path resembles a real workspace. Refresh inventory when membership may have changed, retain selection by identity, and revalidate it at Start. Search only this registered set; do not add a raw Git-branch catalog, a new registration flag or implicit adoption merely for the picker.
- Add explicit parent/child draft state under the existing palette owner (F1). Preserve the parent harness/model/prompt/name and each field's explicit-versus-inherited state while the child opens, submits, fails or completes. Replace `refresh_workspace_form`'s wholesale launch-field replacement with the agreed merge rule: destination defaults may change untouched choices only; dependent defaults must not overwrite an explicit model. Cancel before submission restores the prior destination and focus.
- Reuse the standalone workspace lifecycle job, but change the new child path's `Response::Ok` transition: `accept_lifecycle_job` currently clears `self.palette`; it must retain this child and parent while marking the request accepted (F1). Keep existing provisional/status behavior for unrelated lifecycle operations. Disable duplicate Create and consume pending cancellation without claiming an abort. A hierarchy arrival alone must not close the child or imply success.
- Gate the new child's `try_attach_lifecycle_workspace_from_hierarchy` / `attach_lifecycle_workspace` path as well as acceptance: neither an early hierarchy event nor existing provisional auto-attachment may dismiss the child or select a workspace before the matching successful completion. Preserve the existing attachment behavior outside this new form.
- Retain the project + workspace ID already allocated in the submitted request and its lifecycle correlation token; `LifecycleOutcome::Succeeded` currently contains no returned ID. On matching success, wait for matching registry/hierarchy presence, then select that exact identity and restore the parent draft/focus. Handle completion-before-hierarchy and hierarchy-before-completion, including updates received before acceptance. On Failed, preserve fields and report actual partial state; do not select success just because the workspace appeared. A new created-workspace result variant is unnecessary unless implementation demonstrates a separate need.
- Keep errors and inputs; distinguish failed creation from registered workspace plus failed launch. Retry session launch in place and reconcile ambiguous creation before retry.
- Follow stable checkout identity through branch-label drift, preserve root/existence/ownership guards, and show the shared-agent notice without blocking.
- Separate form-opening availability from selected-target launch eligibility (F3). New agent session must open for a registered project with no selected workspace, or while the current workspace is unavailable/root-drifted, so the user can choose another destination/Create branch. Do not reuse `n`'s current `launch_blocked.or(no_workspace)` gate or `open_create_terminal`'s current-workspace-warning early return on this new entry point. Apply root/existence/ownership/selection guards to Start and preserve the separate Terminal flow's guards. Keep the empty-registry Add/register project route explicit rather than silently selecting a target.
- Change `n` and palette/menu labels/availability consistently through the single key table. Retain separately discoverable New terminal and standalone `w`; preserve terminal-mode input priority and view-handshake behavior.
- Implement a multiline Prompt editor and explicit form-input dispatch (F4). Reuse the existing multiline cursor/editor mechanism where suitable rather than extending a single-line field with accidental Enter-submit behavior. Enter inserts a newline in Prompt; the visible portable submit chord (mockup: Alt+Enter) and Start/Create clicks submit once. Enter in an open picker accepts only its choice. Keep multiline paste as editing, preserve grapheme/cursor editing and consume all modal input/clicks before the underlying terminal. Verify the chord's real encoding rather than relying on a synthetic key event alone.
- Initialize the child with empty Branch plus example placeholder, Project from the selected checkout, and collapsed Workspace options. Reuse asynchronous Git default discovery for Base, without an invalid `feature/` value or silent `main` fallback while lookup is loading/failed. Show the unresolved state and require a resolved default or an explicit valid Base before Create. Test a non-main default and lookup failure. Preserve the existing project-setup/automatic-local-terminal policy; do not start the requested agent from this child.

Exit: state tests and compiled Dashboard/Server integration cover the concrete assertions in the matrix below, including event-order permutations, registry-versus-retained membership, opening versus Start guards, editor dispatch, disconnect/reconciliation, partial failure and every accepted default/edit rule. Check filters actually execute these cases.
