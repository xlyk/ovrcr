# Independent review and corrective follow-ups

The parent declares the independent review required by the actual task or repository policy. Direct coding may require no independent axis, one axis, or both. Pocock implementation uses the installed `code-review` procedure's separate Standards and Spec assignments. Worker checks, worker self-review and native helpers remain worker evidence.

The review target contains the original coding assignment and authenticated publication, complete immutable candidate and source contract digest. The publication supplies the result version. The candidate pins the actual Git base and workspace generation. When an inherited input baseline exists, that authenticated reference remains part of the candidate. A branch name or unchanged HEAD does not identify a complete candidate.

A no-commit candidate includes authorized committed, staged, unstaged and relevant untracked changes, deletions, executable modes and safe symlinks. The Server authenticates that stored candidate and inherited baseline, then publishes ordinary readable before/after/inherited/context files and a bound manifest through the existing private assignment owner. The child reviews those semantic contents with its unchanged read-only tools; it needs no hashing, base64 decoder, Git or shell permission. Review and repair do not create a checkpoint, commit, push or merge.

## Parent operations

1. Collect the worker's immutable coding submission with the common tools. Preserve actual Passed, Failed, Missing and Unrun checks.
2. Call `ovrcr_review` with `Declare`. Supply the exact coding target, required axes, each actual source document with its source kind, reference and SHA256 digest, and optional `context_paths` for necessary unchanged files. Declare a finite repair limit with its provenance. When no limit is supplied, the coordinator records three rounds as its own default. This number is a coordinator choice, not a requirement of the canonical specification or a new human approval. On later candidate declarations, an omitted limit inherits the original applicable limit, provenance and consumed rounds. A declaration cannot silently replace that policy or reset its budget.
3. Call `Assignment` for a required axis. Pass the returned `review_assignment` and `review_scope` to ordinary `ovrcr_start` in a read-only workspace. The review assignment's original immutable contract carries only its own source documents. Standards receives repository rules and the installed method including its Fowler baseline. Spec receives the originating specification or direct brief. Neither receives implementation conversation history or the other axis's findings.
4. Collect each reviewer result, then call `Collect` with its original handle and axis. The Server authenticates the reviewer's original contract, native context and publication. A worker claim, matching label or forged reference does not satisfy review. Findings and outcomes stay separate by axis.
5. If all required review evidence is present and corrective work is safe, call `Repair` with one original request and the captured current child control epoch. The Server saves that finite round and exact corrective brief before calling existing scoped `Followup`. Findings return to the same implementation session, run, conversation, workspace and base. Recover a lost reply by repeating the exact original repair request and epoch.
6. Collect the new worker candidate, declare its exact new target, and assign fresh independent review. Every new declaration binds a new round, including a source/context change against the same candidate. Both required axes need their new round's evidence. Prior reports remain immutable historical evidence and cannot silently satisfy that round.
7. Record explicit acceptance only after required independent reviews and the coding contract's named required worker checks pass. Optional Failed, Missing and Unrun checks remain visible for the parent's separate judgment. Validate the integrated revision separately. Acceptance does not publish, push, merge or grant any later action.

`Stop` records an unresolved stop reason. Repairs stop for exhausted limits, unchanged blocking findings, Missing or Unrun named required checks, blocked decisions or unsafe child attribution. Failed required executable checks can be repaired within scope. Optional check outcomes remain visible and do not widen the declared required-check gates. The parent brings genuine new decisions to its conversation using the existing question path. A new declaration cannot reset a stopped policy or its consumed rounds.

## Capacity and recovery

The parent uses existing capabilities and provider limits. Reserve necessary headroom with the existing `min_free_slots_after_launch` policy before launching implementation work. When only one reviewer slot is available, the parent can perform the declared axes sequentially; no tool waits while holding a slot reservation or the Server mutation lock. Capacity refusal preserves the original reviewer intent and exposes a reason. Ordinary `ovrcr_retry` is allowed only when every predecessor was an authenticated zero-effect capacity refusal that created no native context. Reconcile original handles and successor receipts; never provision a duplicate team or close unrelated sessions.

The existing assignment owner retains the review references, finite policy, consumed rounds and original repair intents. Actual source documents, reports and corrective text remain private immutable task artifacts outside child checkouts. Parent recovery restores those records. Human takeover, conversation replacement, retired workflow authority and Partial or Unknown input retain their existing fences. Review cannot bypass them.

## Evidence boundaries

The owning `pi_delegation::review` suite drives registered production extension tools through the real control client, isolated binary Server, managed fixture PTYs and real Git artifacts. Its deterministic reviewers evaluate the pinned readable untracked artifact, then publish attributable findings. This proves orchestration and attribution. Installed-provider semantic quality and native user-interface acceptance require separate evidence on the reviewed revision. Passing independent review never fills in missing worker checks or missing integrated-revision validation.

The standalone typed-review route is being implemented through the Pi extension. Native publisher adapters with a closed research-only result schema do not thereby support `ResearchSubmission.review`. Before launching such a reviewer, integration must either qualify its actual typed-report schema and validation or refuse the unsupported capability before effects. `read` and `result_file` alone are insufficient. No native typed-review publishing support is claimed by this source-only slice.

Direct independent read-only review contracts remain supported without a coordinator declaration. Their original exact target, source content and publication authenticate through the same owners. Once a coordinator policy governs an implementation, its required context, current target and original reviewer seats apply; stale or invalid policy evidence never falls back to direct admission.

For direct `ovrcr_start`, add optional `review.context_paths` to select necessary
unchanged files. Server Prepare enriches the stored immutable contract with
`review.target.view`, preserving the caller's scope. That view binds the direct
request identity; declared policy views bind the exact declaration round instead.
The parent's original intent remains unchanged. A repeated Prepare uses the stored
view and ordinary contract-byte reconciliation, so moving HEAD or the implementation
checkout never changes that review input. Copy the enriched target from the child
contract into its typed report.
An eligible zero-effect capacity retry retains the original direct view and its
request-bound round through the authenticated retry lineage. It does not prepare
a new view from the current checkout or change the logical contract.

Context permits 32 explicit files and 256 KiB combined decoded bytes, with no
recursive directories. It comes only from the original repository and exact pinned
base. Candidate limits remain 1024 files, 256 KiB combined decoded delta bytes and
512 KiB candidate publication. Axis sources retain their 32-document, 64 KiB each,
128 KiB combined limits. Nothing is omitted or truncated to fit. Necessary binary,
unreadable, missing, private or unsafe content blocks before Launch; reviewers also
report Blocked if a necessary context file was not selected. Modes and symlink
targets are readable data, never executable files or followed links in the view.
The pinned Pi 0.87.1 `read` tool continues by line and cannot return a line above
51,200 UTF-8 bytes. Such a line blocks complete coverage before Launch, including
a source string whose JSON escaping makes its immutable brief line too long.
The Server reports that exact gap; it does not shorten text or grant a shell.
It also blocks ASCII text signatures that the installed tool interprets as GIF or
WebP images, since that tool returns an image notice instead of the complete text.

The Server checks private ownership/modes, manifest and file digests, exact target,
sources, context, axis and round before launch/input, publication and collection. A missing,
tampered, stale or swapped view cannot satisfy Passed review or a dependency edge.
After acceptance is durable, an exact receipt replay still returns that authenticated
receipt under the current identity, target, version, control and authority fences.
Later private-view damage cannot turn that replay into a first acceptance. A first
acceptance still requires the complete current view; replay grants no new input or
acceptance authority and does not rewrite the original receipt.
It prepares Git/content outside the store guard, then publishes bounded immutable
files under the existing current-workflow guard. A retired parent cannot leave new
view files or assignments after that preparation. Private-file publication IO
failures retain their ordinary uncertain effect status and original handle.
Schema 19 protects the new references from older writers. Upgrading leaves old
retained rows and immutable publications unchanged; an old continuation lacking a
readable view reports an explicit gap. A fresh declaration/review can supply new
evidence without reconstructing or rewriting the old report.
